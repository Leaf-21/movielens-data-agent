## 5. ⚠️ 关于时效性维度得分偏低（必须说明）

**Up-to-date 得分 21.5386，明显低于其他四维。这不是缺陷，需要解释清楚。**

### 5.1 计算方式

```
freshness(t) = clamp( (t − T1) / (T2 − T1), 0, 1 )

Up-to-date = 100 × (1 − 时间违规率) × mean(freshness)
```

### 5.2 实测数据

| 项 | 值 |
| --- | --- |
| 时间违规率（第一层） | **0.0** —— 1,000,209 条时间戳全部可解释 |
| 第一层得分 | **100.0000** |
| freshness 合计 | 215,430.829879820289 |
| 参与计算记录数 | 1,000,209 |
| **freshness 均值** | **0.215385814245** |
| **最终得分** | `100.0 × 0.215385814245` = **21.5386** |

### 5.3 freshness 分布（T1/T2 为分位数切点的必然结果）

| 区间 | 条件 | 条数 | 精确占比 | freshness |
| --- | --- | --- | --- | --- |
| 训练期 | `freshness = 0`（`t ≤ T1`） | 700,144 | 69.9998% | 0（clamp 下界） |
| 验证期 | 线性区（含 4 条 `t == T1`） | 150,035 | 15.0004% | 0 ~ 1 线性 |
| 测试期 | `freshness = 1`（`t > T2`） | 150,030 | 14.9999% | 1（clamp 上界） |
| **合计** | — | **1,000,209** | 100% | — |

> 条数按分组后的 `freshness` 值统计，与评分程序实现一致。
> 有 4 条记录的时间戳恰好等于 T1，按程序逻辑归入验证期线性区；
> 若用严格不等式 `t <= T1` 统计会差 4 条。详见 `docs/evaluation-method.md` 第 2.4 节。

### 5.4 为什么这是正常的

1. **T1/T2 按分位数确定，因此 70% 的记录必然落在 T1 之前**，其 freshness 被
   clamp 为 0。这是切分定义的直接后果，与该维度设计无关。
2. 均值 0.2154 的含义是"**整体数据窗口的新近程度约 21.5%**"，是一个客观描述，
   不是"质量差"的判据。
3. 本数据集 **90.4% 的评分集中在 2000 年**（904,082 / 1,000,209），
   时间分布天然偏向早期。

**依据 `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 51 行**：

> "数据年代较早并不必然属于错误。"

因此本维度**不得单独作为"数据质量差"的依据**，在汇报与前端展示中必须配合
上述说明使用。

### 5.5 本维度的局限性

本维度衡量的是"数据在自身时间窗口内的新近程度"，**不是**"数据相对今天的过时程度"。
若评价目标要求"数据必须反映当前状态"，则本数据集（2000–2003）在该意义上
完全不满足 —— 这一事实本报告不回避。

这也是本维度权重被设为 **0.10**（五维中最低档）的原因，
详见 `docs/evaluation-method.md` 第 5.1 节。

## 7. 评价方法与局限

完整的评价方法、40 个检查项定义、权重设计依据与局限说明见
`docs/evaluation-method.md`。以下为要点。

### 7.1 无法验证的情况

| 事项 | 为什么无法验证 |
| --- | --- |
| 用户属性真实性 | `users.dat` 属性由用户自愿填写，GroupLens 未核验 |
| 评分是否反映真实偏好 | 数据集不含行为真值 |
| `Zip-code` 与地区的一致性 | 缺少地区真值参照 |
| 匿名用户的身份 | 用户标识已匿名化 |
| 同名电影是否同一部 | 仅凭标题无法判定，需外部知识库 |
| 时间戳时区 | 数据集未声明时区，本系统统一按 UTC 解释 |
| 评分行为分布是否异常 | 需结合业务背景判断，本系统不作为质量扣分项 |

### 7.2 方法本身的局限

1. **合法性 ≠ 准确性。** Accurate 维度实际衡量"字段值合法率"，
   **不能**等同于"数据真实准确"。格式正确的 `Zip-code` 仍可能是错的。
2. **微平均对字段数敏感。** 已通过"每字段一次机会"缓解，但未做表级加权。
3. **时效性参照系是相对的。** 以 T1/T2 为参照，非绝对时效性（见 5.5）。
4. **完整性分级含主观判断。** "必需字段"的划分基于业务可用性推理。
5. **权重为设计选择，非测量结果。**
6. **得分提升不等于问题全部解决。** 隔离处置会提高得分，但问题只是被移出主数据集。
7. **0–100 不是概率或百分比质量。**

## 9. 本轮开发中修复的缺陷（技术记录）

清洗链路对编码极度敏感，本轮共发现 **6 个缺陷**，其中 3 个与"工具静默处理字节数据"有关。记录于此供后续维护参考。

| # | 缺陷 | 后果 | 修复 |
| --- | --- | --- | --- |
| 1 | 三表格式检查均输出 `total` 指标，汇总时互相覆盖 | 数据规模统计错乱 | reducer 增加表名前缀 |
| 2 | driver 本地模式漏输入重定向，mapper 缺 stdin 直接退出 | reducer 的"补零"把它伪装成合法的 0，**全 0 却不报错** | 改为显式文件读写 + 空输出检测 |
| 3 | 本地模式跨表作业两输入用同一角色 | 参照表被当作评分记录，一致性得分错误降至 49.62（正确 99.87） | 按 `(表名, 角色)` 分别调用 mapper |
| 4 | `MultipleOutputs` 在 Streaming 下不可用 | 清洗分流方案失效 | 改为纯 Python 方案，由 driver 按标签分流 |
| 5 | **字节记录被写成 Python 字面量** `b'...'` | **静默损坏 6040 条用户数据** | 改用二进制流拼接写入 |
| 6 | **`grep` 处理 ISO-8859-1 数据会丢行** | movies 从 3883 行变成 3833 行，**恰好丢掉 50 条含特殊字符的记录** | 改用 `awk` 按字节处理 |

### 9.1 缺陷 5 与 6 的字节级证据

**缺陷 5**（写入时损坏）：

```
c l e a n \t b ' 6 0 4 0 : : M : : 2 5 : : 6 : : 1 1 1 0 6 ' \n
              ^^^                                            ^^^
              多写了 b' 与结尾单引号
```

**缺陷 6**（读取时丢行）：

```
grep: movies.tagged: binary file matches     ← grep 判定为二进制文件
[run_clean] (3833)  total_count(3883)        ← 丢了 50 行
```

50 这个数字与实测的"含非 ASCII 字符的标题数"**完全吻合**，证实了因果。

### 9.2 结论与约束

> **ml-1m 使用 ISO-8859-1 编码，因此整条数据链路上只能使用字节安全的工具。**

缺陷 5 与 6 的共同点是"工具悄悄做了编码或类型转换"：

| 工具 | 隐患 |
| --- | --- |
| Python `%s` 格式化 bytes | 产生 `b'...'` 字面量 |
| `grep` 处理非 ASCII 文件 | 判定为二进制并改变行为 |
| 文本模式读写 | 破坏 ISO-8859-1 编码 |

**后续维护要求**：处理 `.dat` 数据时使用二进制模式读写与 `awk`，避免 `grep`；
Python 中不要对 `bytes` 使用字符串格式化。相关警示已写入代码注释。
