## 2. 数据对象与检查方式

### 2.1 数据规模与格式

| 文件 | 字段 | 编码 | 原始行数 | 其中官方记录 |
| --- | --- | --- | --- | --- |
| `ratings.dat` | `UserID::MovieID::Rating::Timestamp` | ISO-8859-1 | 1,150,241 | 1,000,209 |
| `movies.dat` | `MovieID::Title::Genres` | ISO-8859-1 | 4,465 | 3,883 |
| `users.dat` | `UserID::Gender::Age::Occupation::Zip-code` | ISO-8859-1 | 6,946 | 6,040 |

数据全程按**字节**处理（ISO-8859-1 是单字节编码，`::`、`|`、换行都是单字节），避免转码破坏 `Misérables`、`Léon` 这类标题；读取时不得把首行当表头。

### 2.2 检查项与 Hadoop 作业映射

清洗前/后评分跑的是**同一组 12 个 Hadoop Streaming 作业**，口径完全一致：

| 作业 | 检查内容 | 对应维度 |
| --- | --- | --- |
| `format-ratings` / `format-movies` / `format-users` | 字段数、字段级合法性、取值域 | Accurate / Complete |
| `cross-users` / `cross-movies` | ratings 引用的 UserID/MovieID 是否存在（reduce-side join） | Consistent |
| `group-u-pair` / `group-u-movie` / `group-u-user` | 业务主键重复 | Unique |
| `group-c-movie-multi` / `group-c-user-attr` | 同一主键对应多个不同取值 | Consistent |
| `freshness-ratings` | 新鲜度 `clamp((t−T1)/(T2−T1), 0, 1)` | Up-to-date |

清洗本身也是 Hadoop 作业（`run_clean.sh` 提交 mapper/reducer）：mapper 做字段级判定并输出**业务主键**，靠 MapReduce 的 shuffle 把同一主键的记录聚到一起，reducer 内完成去重与冲突处置。**不是本地脚本处理。**

### 4.1 处置原则

需求要求区分**修复、去重、隔离**，并明确"不得把删除或隔离表述为问题已修复"。本轮边界：

| 处置 | 适用条件 | 本轮命中 |
| --- | --- | --- |
| **修复** | 能**确定**正确值 | 65 |
| **去重** | 整行完全相同（信息不丢失） | 55,739 |
| **隔离** | 无法确定正确值，任何猜测都会引入新错误 | 99,892 |
| **冲突处置** | 主键下多条**字段级合法但取值不同**的记录 | 见 4.3（未解决） |

### 4.3 主键冲突：本轮**没有解决**的问题

**定义**：同一业务主键下存在 ≥2 条字段级合法、但取值不同的记录。例如 `(19, 2692)` 同时出现 `19::2692::1::978146863` 与 `19::2692::4::978146863`——两条都合法，数据本身无法判定哪条是真的。

- 全表冲突主键 **4,328 个**（ratings 4,096 / movies 105 / users 127），涉及记录 63,822 条；
- 处置策略（`rules.json` → `conflict_policy`）**按表区别对待**：
  - `ratings`（事实表）：**整组隔离**。评分是事件记录，隔离不会造成任何引用断裂；反之若"任选一条保留"，实测 4,096 个冲突键里有 3,902 个会选中被注入的值，等于把可疑评分写进数据集。**不确定就不猜。**
  - `users` / `movies`（维表）：**保留一条、其余移除**，因为主键被 `ratings` 引用，整条删除会让原本合法的评分变成孤儿记录（代价更大）。保留规则是确定性的：优先无修复动作、其次非空字段更多、最后取字节序最小，保证结果可复现。
- **保留一条 ≠ 已知真值**：与官方口径对照，movies 有 48 部、users 有 87 位的取值与官方不同——足以说明"保留"只是可复现的选择，不是修正。因此这 4,328 个主键全部计入**未解决问题**（第 7 节）。

## 6. 五维得分与计算依据

评分模型：`得分 = 100 × (1 − 违规记录数 ÷ 适用记录总数)`，同一套程序、同一套阈值跑清洗前后两遍。

### 6.1 Accurate（准确性）= 12 项字段级检查的微平均

| 字段检查 | 清洗前 | 清洗后 |
| --- | --- | --- |
| ratings UserID / MovieID / Rating / Timestamp 非法 | 9,377 / 9,377 / 49,886 / 38,633（÷1,150,241） | 0（÷996,113） |
| movies MovieID 非法 / 标题为空 / 年份不合规 | 29 / 87 / 145（÷4,465） | 0 / 0 / 23（÷3,883） |
| users UserID / Gender / Age / Occupation / Zip 非法 | 45 / 168 / 168 / 168 / 279（÷6,946） | 全部 0（÷6,025） |

→ 清洗前 `100 × (1 − 各项违规率均值) = 97.7423`；清洗后 `= 99.9506`（未满分的唯一原因就是 23 条缺年份标题）。

### 6.2 Complete（完整性）

`= 100 × (1 − 必需字段缺失记录数 ÷ 三表总记录数)`
清洗前 `100 × (1 − 23,342 ÷ 1,161,652) = 97.9906`；清洗后 `23,342 → 0`，得 **100**。

### 6.3 Unique（唯一性）

`= 100 × (1 − 主键违规数 ÷ 三表总记录数)`
清洗前 `100 × (1 − (4,815+495+789) ÷ 1,161,652) = 99.4750`；清洗后 **100**。

### 6.4 Up-to-date（时效性）⚠️ 唯一下降的维度

`= 100 × 时间可解释率 × 新鲜度均值`

| 项 | 清洗前 | 清洗后 |
| --- | --- | --- |
| 时间可解释记录 | 1,111,608 / 1,150,241 = **96.6413%** | 996,113 / 996,113 = **100%** |
| 新鲜度合计 / 参与记录 | 346,333.83 / 1,131,112 = **0.306197** | 211,334.83 / 996,113 = **0.212159** |
| 得分 | `100 × 0.966413 × 0.306197 = 29.5905` | `100 × 1.0 × 0.212159 = 21.2159` |

**下降原因（已核查，不是清洗引入的新问题）**：

1. 清洗前有 **13,503 条毫秒时间戳**（如 `1009669227000`，按秒解释相当于公元三万年）被 clamp 到 freshness = 1；
2. 注入记录中还有大量时间戳落在 `T2` 之后甚至 2100 年（`4102444800`），同样被 clamp 到 1；
3. 这些"假的很新"的记录把清洗前均值抬高到 0.3062，而官方数据的**真实均值是 0.2154**（1,000,209 条口径）。清洗把这些记录隔离或换算后，得分回落到真实水平 21.2159。

即：**清洗前的高分是数据错误造成的假象**。按需求"不得为提高分数擅自改变规则、不要求所有维度都提高"，此项保持原样上报。

### 6.5 Consistent（一致性）= 跨表引用 50% + 表内格式一致性 50%

| 组成 | 清洗前 | 清洗后 |
| --- | --- | --- |
| 跨表引用（users / movies 孤儿记录率均值） | 10,502 与 10,502（÷1,150,241） | 2,994（÷996,113）与 0 |
| 表内一致性（同 ID 多变体、Genres 非法/空、标题空白、Zip 不合规） | 384 / 608 / 224 / 47 / 279 | 全部 0 |
| 得分 | **96.7995** | **99.9249** |

清洗后未能满分，正是 4.3 的冲突与第 5 节的孤儿记录所致——这是**如实反映**，不是计算问题。

| 2 | **隔离导致的孤儿评分** | 2,994 条（涉及 15 个 UserID） | 这 15 位用户的 Zip-code 无法确定正确值，连带影响其名下评分。 |
| 3 | 电影标题缺年份 | 23 条 | 信息不足，需外部资料；不臆造。 |
| 4 | 用户属性真实性（Gender/Age/Occupation/Zip） | 全部 6,025 行 | 用户自愿填写且未经核验，**格式合法 ≠ 内容真实**。 |
| 5 | 评分是否反映真实偏好 | 全部 996,113 条 | 数据不含行为真值，无法从数据内部判定。 |
| 6 | 邮编与地区匹配、同名电影是否同一部、匿名用户是否同一人 | — | 缺少外部参照。 |

## 8. 结果可信度验证（"Hadoop 是不是真的在处理数据"）

| # | 验证方式 | 结果 |
| --- | --- | --- |
| 1 | 清洗作业读入行数 vs 输入文件真实行数（driver 内建校验） | ratings 1,150,241、movies 4,465、users 6,946 **完全一致** |
| 2 | 分流结果 vs reducer 统计逐标签核对 | 四个标签全部一致，`unknown_count = 0` |
| 3 | 口径自洽：`输入 = 输出 + 去重移除` | 三表全部成立（如 ratings：1,150,241 = 1,095,075 + 55,166） |
| 4 | 与官方口径（v1）逐条对照 | ratings 清洗结果**全部落在官方记录集合内**（0 条自造记录），仅比官方少 4,096 条冲突隔离记录；movies / users 行数与官方清洗结果完全一致（3,883 / 6,025） |
| 5 | 检查类作业的"假成功"防护 | 格式作业必须报告记录总数，否则判失败；空输出一律判失败 |
| 6 | 环境能力校验 | `Map input records` 等计数器与文件行数交叉一致；作业在真实 MapReduce（`LocalJobRunner`）上执行 |

> 第 1、3 项是本轮新增的**硬校验**：只要 Hadoop 读了别的文件、少读了几行或提前退出，driver 会直接判定清洗失败，而不是产出一份"看起来成功"的报告。

## 9. 评价方法的适用边界与局限

1. **"格式正确"不等于"内容真实"**：本方法只能验证格式、取值域、引用关系与唯一性，无法验证用户属性与评分的真值。
2. **隔离会改变分母**：清洗前后记录数不同（1,161,652 → 1,006,021），得分是"各自口径下的内部违规率"，不是绝对质量的直接比较。
3. **权重是设计选择**：0.25/0.25/0.15/0.10/0.25 为人为设定，改变权重会改变综合分排序；`up_to_date` 权重最低（0.10），因为它衡量的是数据新近程度而非错误率（见 `docs/evaluation-method.md` 第 5.1 节）。
4. **冲突处置是折中**：ratings 整组隔离会损失 0.41% 的合法评分（4,096 条），维表保留一条会带来约 135 条无法验证的属性取值。两种代价都已在第 4.3、7 节量化。
5. **毫秒时间戳的判定阈值**（>10¹¹ 视为毫秒）是本项目的工程约定；若时间戳单位混淆方式更复杂（如微秒、随机偏移），本规则不足以覆盖。
