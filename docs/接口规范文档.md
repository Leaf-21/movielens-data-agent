# 接口规范文档

## 一、文档目的

本文档用于统一三人团队在“Agent 驱动的 Hadoop 数据清洗与五维质量评估系统”开发过程中的接口规范。

项目整体分为三个模块：

```text
Frontend
   ↓
Agent
   ↓
Hadoop Tool
   ↓
Hadoop
```

其中：

- Hadoop 负责实际的数据处理与质量评分；
- Agent 负责理解用户需求、组织任务、调用 Hadoop、解释结果；
- Frontend 负责用户输入、任务状态展示、评分展示和结果交互。

这一职责划分来自项目需求文档。

本文档的目标是使三个模块可以**并行开发、独立测试、统一联调**。

------

# 二、接口设计原则

## 2.1 模块职责独立

三个模块之间通过明确的接口交换数据。

```text
前端
只负责：
输入 + 展示

Agent
负责：
理解 + 调度 + 解释

Hadoop
负责：
计算 + 清洗 + 评分
```

前端不直接调用 Hadoop。

Agent 不直接实现 Hadoop 中的数据清洗算法。

Hadoop 不负责生成面向用户的自然语言解释。

------

## 2.2 结果必须来自实际执行

接口返回的评分、数据量和清洗结果必须来自实际执行结果。

不得：

- 手工填写评分；
- 使用测试占位数据冒充真实结果；
- 在 Hadoop 执行失败时返回成功结果；
- 为提高评分而修改评分规则。

项目需求明确要求系统不得编造分数或处理结果。

------

## 2.3 接口格式统一

本团队统一使用：

```text
JSON
UTF-8
REST API
HTTP
```

具体 HTTP 接口属于本团队新增技术约定，并非原始需求文档已经规定的内容。

------

# 三、总体接口结构

```text
┌──────────────────────┐
│      Frontend        │
│      前端页面         │
└──────────┬───────────┘
           │
           │ HTTP/JSON
           ▼
┌──────────────────────┐
│       Agent          │
│ 需求解析/任务调度/解释 │
└──────────┬───────────┘
           │
           │ Tool / API
           ▼
┌──────────────────────┐
│     Hadoop Tool      │
│ Hadoop任务封装接口     │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│       Hadoop         │
│ 清洗 + 五维评分        │
└──────────────────────┘
```

# 四、Frontend → Agent 接口

## 4.1 创建任务

### 接口

```text
POST /api/tasks
```

### 功能

前端向 Agent 提交用户的自然语言数据治理需求。

项目需求要求用户通过自然语言输入清洗和评估需求，并由 Agent 自动完成后续流程。

### Request

```json
{
  "prompt": "请使用默认规则清洗 MovieLens 1M，评估清洗前后的五个数据质量维度。",
  "data_version": "movielens-1m-v1",
  "rule_version": "default",
  "score_config": null
}
```

字段说明：

| 字段           | 类型   | 必填 | 说明             |
| -------------- | ------ | ---- | ---------------- |
| `prompt`       | String | 是   | 用户自然语言需求 |
| `data_version` | String | 是   | 原始数据版本     |
| `rule_version` | String | 否   | 清洗规则版本     |
| `score_config` | Object | 否   | 评分配置         |

当用户没有指定清洗规则或评分方案时，使用系统已经登记的默认方案。

------

# 五、Agent → Frontend 创建任务响应

### Response

```json
{
  "task_id": "task_20260926_0001",
  "status": "PENDING",
  "message": "任务已创建"
}
```

### 字段说明

| 字段      | 类型   | 说明             |
| --------- | ------ | ---------------- |
| `task_id` | String | 本次任务唯一标识 |
| `status`  | String | 当前任务状态     |
| `message` | String | 状态说明         |

------

# 六、任务状态接口

## 6.1 查询任务状态

```text
GET /api/tasks/{task_id}
```

例如：

```text
GET /api/tasks/task_20260926_0001
```

### Response

任务执行中：

```json
{
  "task_id": "task_20260926_0001",
  "status": "RUNNING",
  "stage": "CLEANING",
  "message": "正在执行 Hadoop 数据清洗"
}
```

任务完成：

```json
{
  "task_id": "task_20260926_0001",
  "status": "SUCCESS",
  "stage": "COMPLETED",
  "message": "任务执行完成"
}
```

任务失败：

```json
{
  "task_id": "task_20260926_0001",
  "status": "FAILED",
  "stage": "QUALITY_SCORE",
  "message": "清洗后质量评分执行失败"
}
```

项目需求明确要求用户能够了解任务是否正在执行、已经完成或执行失败；发生异常时，需要说明失败环节和原因。

------

# 七、任务状态统一定义

本团队统一使用以下状态：

| 状态      | 含义                 |
| --------- | -------------------- |
| `PENDING` | 任务已创建，尚未执行 |
| `RUNNING` | 任务正在执行         |
| `SUCCESS` | 任务执行成功         |
| `FAILED`  | 任务执行失败         |

执行阶段使用：

| 阶段              | 含义         |
| ----------------- | ------------ |
| `PARSE_REQUEST`   | 解析用户需求 |
| `BEFORE_SCORE`    | 清洗前评分   |
| `CLEANING`        | 执行数据清洗 |
| `AFTER_SCORE`     | 清洗后评分   |
| `GENERATE_REPORT` | 生成评估报告 |
| `COMPLETED`       | 完成         |

------

# 八、Agent → Hadoop Tool 接口

这一层的具体技术实现方式原需求没有规定，因此以下内容属于**本团队新增约定**。

Agent 将 Hadoop 的清洗和评分能力封装为三个主要工具：

```text
quality_score_before()
clean_dataset()
quality_score_after()
```

也可以由团队根据实际 Hadoop 实现改为其他函数名，但三个功能必须存在。

------

# 九、清洗前质量评分接口

```text
POST /hadoop/quality-score/before
```

### Request

```json
{
  "task_id": "task_20260926_0001",
  "data_version": "movielens-1m-v1",
  "score_config": {
    "accurate": true,
    "complete": true,
    "unique": true,
    "up_to_date": true,
    "consistent": true
  }
}
```

### Response

```json
{
  "task_id": "task_20260926_0001",
  "status": "SUCCESS",
  "data_version": "movielens-1m-v1",
  "scores": {
    "accurate": 0,
    "complete": 0,
    "unique": 0,
    "up_to_date": 0,
    "consistent": 0
  }
}
```

注意：

五维评分的**具体计算公式、权重和分值范围目前原需求文档没有统一规定，需要由成员A设计并由团队确认**。

------

# 十、Hadoop 数据清洗接口

```text
POST /hadoop/clean
```

### Request

```json
{
  "task_id": "task_20260926_0001",
  "data_version": "movielens-1m-v1",
  "rule_version": "rule-v1"
}
```

### Response

```json
{
  "task_id": "task_20260926_0001",
  "status": "SUCCESS",
  "input_version": "movielens-1m-v1",
  "output_version": "movielens-1m-v1-clean-v1",
  "rule_version": "rule-v1",
  "statistics": {
    "before_count": 0,
    "after_count": 0,
    "fixed_count": 0,
    "deduplicated_count": 0,
    "isolated_count": 0
  }
}
```

其中：

- `fixed_count`：修复的数据量；
- `deduplicated_count`：去重的数据量；
- `isolated_count`：隔离的数据量。

项目要求前端区分修复、去重和隔离，并解释数据量变化，不能把删除或隔离直接表述为“问题已经修复”。

------

```text
POST /hadoop/quality-score/after
```

### Request

```json
{
  "task_id": "task_20260926_0001",
  "data_version": "movielens-1m-v1-clean-v1",
  "score_config": {
    "accurate": true,
    "complete": true,
    "unique": true,
    "up_to_date": true,
    "consistent": true
  }
}
```

### Response

```json
{
  "task_id": "task_20260926_0001",
  "status": "SUCCESS",
  "data_version": "movielens-1m-v1-clean-v1",
  "scores": {
    "accurate": 0,
    "complete": 0,
    "unique": 0,
    "up_to_date": 0,
    "consistent": 0
  }
}
```

清洗前后必须使用同一套评价口径，以保证结果可比较。

------

# 十二、五维质量评分统一字段

统一使用以下英文字段：

```json
{
  "accurate": 0,
  "complete": 0,
  "unique": 0,
  "up_to_date": 0,
  "consistent": 0
}
```

对应关系：

| 字段         | 中文   | 原需求名称 |
| ------------ | ------ | ---------- |
| `accurate`   | 准确性 | Accurate   |
| `complete`   | 完整性 | Complete   |
| `unique`     | 唯一性 | Unique     |
| `up_to_date` | 时效性 | Up-to-date |
| `consistent` | 一致性 | Consistent |

这五个维度的定义来自原项目需求。

    "complete": 0,
    "unique": 0,

------

# 十四、评估报告结构

`report` 统一包含：

```json
{
  "method": "五维质量评分方法说明",
  "improvements": [],
  "unresolved": [],
  "limitations": []
}
```

其中：

### `method`

说明：

- 五维评分如何计算；
- 评价范围；
- 分值范围；
- 指标依据。

### `improvements`

说明清洗后哪些方面发生变化。

例如：

```json
[
  {
    "dimension": "complete",
    "description": "关键字段缺失率下降"
  }
]
```

### `unresolved`

说明仍然无法解决的问题。

### `limitations`

说明哪些情况无法验证。

项目明确要求 Agent 解释五个维度的前后变化、已经解决的问题、仍存在的问题以及评价局限。

------

# 十五、错误响应规范

所有接口发生错误时统一返回：

```json
{
  "task_id": "task_20260926_0001",
  "status": "FAILED",
  "error": {
    "code": "HADOOP_EXECUTION_ERROR",
    "message": "Hadoop 数据清洗执行失败"
  }
}
```

错误码建议：

| 错误码                   | 说明             |
| ------------------------ | ---------------- |
| `INVALID_REQUEST`        | 请求参数错误     |
| `DATA_NOT_FOUND`         | 数据不存在       |
| `INVALID_DATA_VERSION`   | 数据版本错误     |
| `INVALID_RULE_VERSION`   | 清洗规则版本错误 |
| `HADOOP_EXECUTION_ERROR` | Hadoop 执行失败  |
| `QUALITY_SCORE_ERROR`    | 评分失败         |
| `AGENT_EXECUTION_ERROR`  | Agent 执行失败   |
| `INTERNAL_ERROR`         | 系统内部错误     |

执行失败时必须返回实际错误，不允许使用默认评分或虚假结果替代。

------

# 十六、数据版本规范

数据版本由：

```text
数据集名称 + 版本
```

构成。

例如：

```text
movielens-1m-v1
```

清洗后：

```text
movielens-1m-v1-clean-v1
```

规则版本：

```text
rule-v1
```

后续如果清洗规则发生变化：

```text
rule-v2
```

原需求特别要求统一记录数据版本和清洗规则版本，并要求后续迭代不要混用不同数据版本或时间范围的产物。

------

# 十七、T1 / T2 规范

系统必须保存：

```text
T1：训练期截止时间
T2：验证期截止时间
```

测试数据应位于：

```text
T2 之后
```

接口统一：

```json
{
  "T1": "YYYY-MM-DD",
  "T2": "YYYY-MM-DD"
}
```

具体日期由项目成员结合数据集和实验设计确定，本文档不预先规定日期。

------

# 十八、三人开发对应接口

## 成员A：Hadoop

负责：

```text
POST /hadoop/quality-score/before
POST /hadoop/clean
POST /hadoop/quality-score/after
```

确保：

- 实际通过 Hadoop 执行；
- 输出真实评分；
- 输出数据量；
- 输出处理统计；
- 返回统一 JSON。

------

## 成员B：Agent

负责：

```text
POST /api/tasks
GET  /api/tasks/{task_id}
GET  /api/tasks/{task_id}/result
```

负责调用成员A提供的 Hadoop 接口。

------

## 成员C：Frontend

只调用 Agent 接口：

```text
POST /api/tasks

GET /api/tasks/{task_id}

GET /api/tasks/{task_id}/result
```

前端不直接依赖 Hadoop 的内部实现。

------

# 十九、接口联调顺序

三人不需要等待全部代码完成，可以按以下顺序同步开发。

### 第一阶段

成员A先确定 Hadoop 返回 JSON。

```text
Hadoop
   ↓
JSON
```

成员B根据 JSON 开发 Agent。

成员C可以根据相同 JSON 编写前端 Mock 数据。

### 第二阶段

成员A完成 Hadoop 实际实现。

成员B接入真实 Hadoop。

成员C继续完成页面。

### 第三阶段

三人进行联合测试：

```text
Frontend
 ↓
Agent
 ↓
Hadoop
 ↓
真实数据
 ↓
评分结果
 ↓
Agent
 ↓
Frontend
```

### 第四阶段

确认三层返回结果一致后合并到 `main`。

------

# 二十、接口变更规范

接口已经被三人使用后，不允许随意修改字段。

例如：

原来：

```json
{
  "before_score": {}
}
```

不能直接改成：

```json
{
  "score_before": {}
}
```

如确实需要修改，必须：

1. 在 GitHub Issue 中说明原因；
2. 通知相关成员；
3. 修改接口文档；
4. 修改调用方；
5. 完成联调测试；
6. 再通过 Pull Request 合并。

# 二十三、接口完成标准

当满足以下条件时，认为接口开发完成：

-  Frontend 可以创建任务；
-  Agent 可以生成 `task_id`；
-  Frontend 可以查询任务状态；
-  Agent 可以调用 Hadoop；
-  Hadoop 可以执行清洗前评分；
-  Hadoop 可以执行数据清洗；
-  Hadoop 可以执行清洗后评分；
-  Agent 可以获取完整结果；
-  Frontend 可以展示完整结果；
-  所有接口使用统一 JSON；
-  错误状态能够正常返回；
-  数据版本和规则版本能够传递；
-  `T1/T2` 能够传递；
-  清洗前后五维评分能够进行对比；
-  失败时不会生成占位结果。

------

# 二十四、接口文档维护原则

接口文档是三人并行开发的共同依据。

因此：

**先确定接口，再进行跨模块开发；接口发生变化时，先更新文档，再修改代码。**

最终 GitHub 仓库形成：

```text
代码
+
Issue
+
Commit
+
Pull Request
+
接口文档
+
测试记录
```

从而保证三个人能够在不同分支中同时开发，并在最终阶段完成统一联调。
