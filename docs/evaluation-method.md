## 0. 为什么从 v1 切到 v2（本版口径变更说明）

本文档上一版的所有实测数字都来自 **GroupLens 官方未改动版本** `movielens-1m-v1`：规模按 1,000,209 / 3,883 / 6,040 计，结构完整性与字段级合法性检查的违规数几乎全为 0，`Zip-code` 仅 81 条不合规。在**未改动**的官方数据上做清洗与评分，必然得到"数据几乎无问题"的结论——**清洗实验本身失去意义**。

本轮改用**课程给定版本** `movielens-1m-v2`（版本登记见 `data/DATASETS.md`）：

| 项 | 上一版（v1，错误口径） | 本版（v2，正确口径） |
| --- | --- | --- |
| 数据 | GroupLens 官方 `ml-1m` 原样文件（`movielens-1m-v1`） | 课程给定版本（`movielens-1m-v2`） |
| 实测规模（三表） | 1,000,209 / 3,883 / 6,040 | **1,150,241 / 4,465 / 6,946** |
| 实测结论 | "几乎无违规，只需处置 `Zip-code`" | **13 类问题**，99,892 条需隔离、55,739 条需去重 |

把 v2 与 v1 逐条做集合比对，官方记录**一条不少**地存在于 v2 中（ratings 1,000,209 条、movies 3,883 条全部命中），多出来的部分正好构成本文档 2.3 节列出的每一类问题（分隔符被替换、`::EXTRA_FIELD`、评分写成 `five`/`3.5`、毫秒时间戳、`1000000+ID`、重复与主键冲突、`Gender=X`、`UnknownGenre` 等）。

**口径结论：**

- `movielens-1m-v1` 仅保留作"清洗是否无损还原"的**对照基准**（官方口径 1,000,209 条），不再作为评价对象；
- 清洗规则由上一版规则升级为 **`rule-v2`**：新增解析容错、毫秒时间戳识别与换算、标识符取值域判定、`Genres` 域校验、"完全重复"与"主键冲突"的区分（逐条变更见 `hadoop/config/rules.json` 的 `_rule_v2_changelog`，检查口径见本文 4.0 节）；
- 清洗后数据版本为 **`movielens-1m-v2-clean-v1`**，任务标识 **`task_002`**，全部指标由 Hadoop 作业实测；
- 本文档中凡出现 v1 口径的数字，**必须标注"官方口径对照值"**，不得与 v2 实测值混用（依据 `data/DATASETS.md` 注意事项第 1 条"不要把 v1 与 v2 的产物混用"）。

## 1. 目的与依据

### 1.1 本文档解决什么问题

系统需要"清洗前后五维评分对比"，而对比要成立，前提是**有一套明确、可复现、清洗前后完全一致的评价口径**。本文档就是这套口径的定义：

- 每个维度的**含义**、**可计算指标**、**计算公式**
- 每个维度的**分值范围**与**权重**，以及是否设置综合分
- 本次评价**覆盖不了什么**（无法验证的情况与局限）

### 1.2 文档依据

| 要求 | 出处 |
| --- | --- |
| 五维含义由文档给出，具体指标/打分方法/分值范围/权重/是否设综合分**由学生自主设计** | `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 55 行 |
| **学生需自行提出评分方案，说明设计依据**，并通过 Hadoop 实现 | 同上 第 65 行 |
| 需说明**评价方法、适用范围和局限**；未完成、无法评价、未验证的情况应清楚标注 | 同上 第 108 行 |
| 需输出**仍未解决的问题及评价局限** | `docs/引言_项目总体要求与汇报安排.md` 第 22 行 |
| 具体指标和计算公式**由成员A负责提出**，与另两名成员讨论确认 | `docs/迭代一项目分工文档.md` 第 120 行 |
| 最终验收需展示**评价方法及局限** | 同上 第 542 行 |
| 清洗前后**必须使用同一套评价口径**，使结果可比较 | `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 69 行 |
| **不要求所有维度的分数都提高，也不预设必须达到的分数** | 同上 第 69 行 |

### 1.3 一条前置设计原则（重要）

- 本文档的指标**先定义、后测量**，不得在看到结果后回头调整公式或权重来制造"分数提升"。
- 若某维度清洗前后得分相同，**如实记录并解释原因**，不视为缺陷（依据：第 69 行）。
- 若某维度**无法有效评价**，标注为"不适用/证据不足"，不强行给分。

**（b）这些问题不是零星噪声，而是成规模注入**

- 与官方口径对照：v2 的 ratings 1,150,241 条中有官方 1,000,209 条，注入 **150,032** 条；movies 4,465 = 官方 3,883 + 注入 582；users 6,946 = 官方 6,040 + 注入 906；
- `ratings` 的 `(UserID, MovieID)` 唯一组合数只有 **1,021,932**，小于结构合法行数 1,136,738，说明重复与冲突是**成片出现**的；
- 处置规模：需**隔离** **99,892** 条、需**去重** **55,739** 条、能确定正确值而**修复**的仅 **65** 条（全部是 `users` 的 ZIP+4）。

**（c）由此得出的设计结论**

1. **"脏数据类"问题（字段错、值越界、重复、关联断裂）在本数据集中大量存在。** 按常见思路设计的去重、越界、引用完整性规则都不会是"跑出 0 条"，13 类问题中仅第 1、6 类的主要部分可确定性修复。
2. **可确定性修复的只有三类**：解析层问题（分隔符被替换、行尾多余字段）、毫秒时间戳、ZIP+4。其余问题属"值不可信"，任何猜测都会引入新错误，必须**隔离**——依据迭代一需求第 91 行，"隔离"**不得**表述为"已修复"。
3. 因此本方案的预期是：**Accurate / Complete / Unique / Consistent 四维得分提升，Up-to-date 反而下降**。下降的原因是清洗把被异常时间戳抬高的假分数还原为真实水平（推导见 4.4），依据本文档 1.3 节与迭代一需求第 69 行"不要求所有维度的分数都提高"，这属于**如实报告的真实结论**，不得通过人为调整规则来制造全面改善。

### 2.4 T1 / T2 时间边界

依据 `docs/引言_项目总体要求与汇报安排.md` 第 11 行与 `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 13 行，迭代一需统一确定 `T1/T2`，后续迭代不得混用。本版取值已确定并写入 `hadoop/config/rules.json` 的 `time` 段，`task_002` 的全部作业（清洗前评分、清洗、清洗后评分）均使用该取值。

| 边界 | 取值 | Unix 时间戳 | 含义 | 数据占比 |
| --- | --- | --- | --- | --- |
| **T1** | **2000-11-22** | **974862386** | 训练期截止时间 | 70% |
| **T2** | **2000-12-10** | **976422054** | 验证期截止时间 | 15% |
| 测试期 | `> T2` | — | 测试数据位于 T2 之后 | 15% |

**切分方法：分位数必须在「清洗后合法记录」上计算。** 按清洗后合法 `ratings.Timestamp` 的实际分位数取 70% 与 85% 位置（不是按时间跨度等分）。原始 v2 数据含 13,503 条毫秒时间戳、6,001 条越界时间戳（含 2100 年）与 9,377 条非数字时间戳，直接在原始数据上取分位会把切点拉偏——这一点已写入 `rule-v2` 的 `time._derivation`。

**实测取值：** 在清洗后 996,113 条合法记录上重算，仍得到 `T1 = 974862386`（**2000-11-22**）、`T2 = 976422054`（**2000-12-10**）。

**实测划分效果（清洗后 996,113 条）：**

| 集合 | 条件 | 条数 | 精确占比 |
| --- | --- | --- | --- |
| 训练期 | `t ≤ T1` | **700,148** | 70.29% |
| 验证期 | `T1 < t ≤ T2` | **150,031** | 15.06% |
| 测试期 | `t > T2` | **145,934** | 14.65% |
| **合计** | — | **996,113** | 100% |

**❌ 一个已被否决的方案（记录在案，避免重犯）：**

最初曾按「时间跨度的 70%/85% 位置」提出 `T1=2002-04-23`、`T2=2002-09-25`。该方案**错误**，原因是假设了数据在时间上均匀分布，而实际数据 **90% 以上集中在 2000 年**（清洗后 2000 年仍占 90.5%）。

| 切分口径 | 测试集占比 | 判定 |
| --- | --- | --- |
| 时间跨度的 70%/85% 位置 | **0.76%** | ❌ 远不足以支撑迭代二的分类/聚类评估与迭代三的图分析 |
| 时间戳分位数 70%/85%（本方案） | **14.65%**（145,934 条） | ✅ 已采用 |

详见 `reports/quality-report/data-analysis-report.md` 第 6 节。

> **⚠️ 必须澄清的语义（关系到整套设计是否自相矛盾）**
>
> `T1/T2` **不是"数据有效期的截断线"**，不能因为"某条评分发生在 2001 年"就判定它"不新鲜"或把它当作清洗对象删除。
> 依据：`docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 51 行明确"**数据年代较早并不必然属于错误**"。
>
> `T1/T2` 的真实用途有两个：
> 1. 供**后续迭代**划分训练/验证/测试窗口（迭代二训练分类器需用）；
> 2. 作为本文档 **Up-to-date 维度的参照基准**（用"距 T2 的时间距离"衡量，而非"距今天"）。

## 3. 总体设计思路

### 3.1 评分层级

```
字段级检查  →  表级（文件级）率值  →  维度得分（0–100）  →  五维汇总
```

每个维度得分统一映射到 **0–100**，便于对比与展示。

### 3.2 为什么采用"违规率扣分"而非"直接给分"

采用 `得分 = 100 × (1 − 违规记录数 ÷ 适用记录总数)` 的形式，理由：

1. **可解释**：得分直接对应"多少条数据有问题"，Agent 能据此生成人类可读的解释。
2. **可比较**：清洗前后分母可能变化，因此分母分别取各自表的总记录数，并在报告中同时给出绝对条数。
3. **可复现**：公式只依赖原始数据与规则，不依赖人工判断。

### 3.3 与清洗处置的对应关系

| 处置方式 | 含义 | 对得分的影响 |
| --- | --- | --- |
| **修复** | 能确定正确值并改回 | 该违规项在 After 中消失，得分提升 |
| **去重** | 完全重复的业务记录（整行字节级相同） | 记录数减少，**信息不丢失**，得分提升 |
| **冲突处置** | 同一主键下多条字段级合法但**取值不同**的记录 | 按表区别对待：`ratings` 整组隔离、`users`/`movies` 保留一条（见 4.3）；**该问题未真正解决** |
| **隔离** | 疑似错误但无法确证，移出主数据集 | 记录数减少，得分提升（需在报告中说明是"隔离"而非"修正"） |
| **删除** | 确定无意义且不可恢复 | 记录数减少，得分提升 |

> 依据 `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 91 行：**避免将删除或隔离记录直接表述为"问题已修复"**。因此每个统计口径都必须**分别输出** `fixed_count` / `deduplicated_count` / `isolated_count`，`rule-v2` 另输出 `conflict_key_count`（主键冲突涉及的主键数，全部计入未解决问题）。

**本轮实测命中量（`task_002`）：** 修复 **65**、去重移除 **55,739**、隔离 **99,892**、主键冲突 **4,328** 个主键（涉及记录 63,822 条）。

### 4.0 解析层容错（`rule-v2` 新增的前置检查）

字段级检查的前提是**记录能被正确切成字段**。`rule-v2` 在字段级检查之前增加了解析容错层：能确定性还原的**修复**，不能还原的**隔离**（依据迭代一需求第 91 行，不得把隔离写成修复）。

| 编号 | 检查项 | 判据 | 处置 |
| --- | --- | --- | --- |
| P1 | 分隔符一致性 | 标准分隔符为 `::`；被替换为 `,`、`\|`、`:` 时，若能还原出标准字段数 | **修复**（还原分隔符） |
| P2 | 行尾多余字段 | 行尾多出 `::EXTRA_FIELD` 这类不含业务信息的字段 | **修复**（截断） |
| P3 | 字段数 | `ratings` = 4、`movies` = 3、`users` = 5 | 结构合法方可进入字段级检查；无法还原者**隔离** |

**实测（清洗前）：** 结构异常 ratings **13,503**（6,001 条分隔符被替换、3,751 条行尾多 `::EXTRA_FIELD`、3,751 条缺 1 个字段）、movies **70**、users **108**；清洗后可还原的已修复、不可还原的已隔离，三表结构异常均为 **0**。

> 解析层**不单独计入 4.1 的 12 项微平均**（它的作用是决定记录能否进入字段级检查），但命中量单独输出，见 5.3 节。标识符取值域（`users` 1–6040、`movies` 1–3952）是另一项前置判定，归入一致性维度的 C3（见 4.5）。

### 4.1 Accurate（准确性）

**文档含义**：数据的值应当真实反映现实世界的情况，避免错误或失真的信息。

**可评价部分**：字段值的**合法性**（是否落在文档规定的取值域内）。这是本轮唯一可自动验证的准确性层面。

| 编号 | 检查项 | 判据 | 适用范围 |
| --- | --- | --- | --- |
| A1 | `UserID` 为正整数 | 匹配 `^[1-9][0-9]*$` | ratings、users |
| A2 | `MovieID` 为正整数 | 匹配 `^[1-9][0-9]*$` | ratings、movies |
| A3 | `Rating` 为 1–5 的整数 | 匹配 `^[1-5]$` | ratings |
| A4 | `Timestamp` 为可解释的正整数 | 匹配 `^[0-9]+$` 且落在 2.2 实测范围内。**`rule-v2` 新增单位混淆判定**：取值 `> 10¹¹` 视为**毫秒**，整除 1000 换算为秒后再校验；换算后仍越界则隔离 | ratings |
| A5 | `Gender` 属于 `{M, F}` | 集合成员判定 | users |
| A6 | `Age` 属于 `{1,18,25,35,45,50,56}` | 集合成员判定 | users |
| A7 | `Occupation` 为 0–20 的整数 | 匹配 `^(1[0-9]|[0-9])$` 且 ≤ 20 | users |
| A8 | `Zip-code` 形如 5 位数字 | 匹配 `^[0-9]{5}$` | users |
| A9 | `Title` 非空 | 去除首尾空白后长度 > 0 | movies |
| A10 | `Title` 结尾含同年份 `(YYYY)` | 匹配 `\((\d{4})\)\s*$` 且年份在 1900–2003 | movies |

**公式：**

```
Accurate = 100 × (1 − Σ_check |V_check| ÷ Σ_check |R_check|)
```

即对所有检查项做**微平均**（每个字段一次机会），避免字段数多的表主导整体得分。

**实测结果（对应第 2.3 节，`task_002`）：** 12 项检查在清洗前**全部有违规**，清洗后除 A10 外全部归零。

| --- | --- | --- | --- |
| A1 `UserID`（ratings） | 1,150,241 | **9,377** | 0（÷996,113） |
| A2 `MovieID`（ratings） | 1,150,241 | **9,377** | 0（÷996,113） |
| A3 `Rating` | 1,150,241 | **49,886** | 0（÷996,113） |
| A4 `Timestamp` | 1,150,241 | **38,633** | 0（÷996,113） |
| A1 `UserID`（users） | 6,946 | **45** | 0（÷6,025） |
| A5 `Gender` | 6,946 | **168** | 0（÷6,025） |
| A6 `Age` | 6,946 | **168** | 0（÷6,025） |
| A7 `Occupation` | 6,946 | **168** | 0（÷6,025） |
| A8 `Zip-code` | 6,946 | **279** | 0（÷6,025） |
| A2 `MovieID`（movies） | 4,465 | **29** | 0（÷3,883） |
| A9 `Title` 非空 | 4,465 | **87** | 0（÷3,883） |
| A10 `Title` 结尾年份 | 4,465 | **145** | **23**（÷3,883，信息不足、处置为 `keep`） |

- 清洗前得分：`100 × (1 − 12 项违规率均值) = ` **97.7423**；
- 清洗后得分：**99.9506** —— 未满分的唯一原因就是那 23 条缺结尾年份的标题。

### 4.2 Complete（完整性）

**文档含义**：衡量业务所必需的数据是否完整，例如不能缺失的字段是否存在空值。

**关键问题**：哪些字段是"必需"的？本方案分级定义：

| 级别 | 字段 | 理由 |
| --- | --- | --- |
| **必需（缺失即违规）** | ratings：全部 4 字段；users：`UserID`；movies：`MovieID`、`Title` | 缺任一则记录无法定位或无法参与下游分析 |
| **属性（缺失单列统计，不计入扣分）** | users：`Gender`、`Age`、`Occupation`、`Zip-code` | 属于自愿填写的画像信息，缺失反映"信息不足"而非"数据错误" |
| **可选** | movies：`Genres` | 缺失不影响记录唯一性，仅影响类型维度分析 |

**⚠️ 该分级是本文档的一个设计决策**，依据 `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 51 行"应区分真正的数据错误、**信息不足**和正常的业务现象"。把"用户没填邮编"算作数据错误会系统性低估数据质量。

**公式：**

```
Complete = 100 × (1 − |R_missing_required| ÷ |R_total|)
```

其中 `R_missing_required` 为"任一必需字段为空/全空白/含缺失标记（如 `NA`、`NULL`、`?`、空串）"的记录集合。

**同时输出**（不计入得分，但写入报告，供 Agent 解释）：

```
OptionalFillRate(Zip-code)  = 非空 Zip-code 记录数 ÷ users 总记录数
OptionalFillRate(Genres)    = 非空 Genres 记录数   ÷ movies 总记录数
```

**实测结果（`task_002`）：**

| 项 | 清洗前 | 清洗后 |
| --- | --- | --- |
| `ratings` 必需字段缺失 | **23,255** | 0 |
| `movies` 必需字段缺失（标题为空） | **87** | 0 |
| `users` 必需字段缺失（`UserID`） | 0 | 0 |
| 缺失记录数 ÷ 总记录数 | **23,342 ÷ 1,161,652** | **0 ÷ 1,006,021** |
| 得分 | `100 × (1 − 23,342 ÷ 1,161,652)` = **97.9906** | **100.0000** |

**填充率（不计入得分）：** `Zip-code` 清洗前 6,847 ÷ 6,946（98.6%）、清洗后 6,025 ÷ 6,025（100%）；`Genres` 清洗前有 50 条为空、清洗后 0（该 50 条随 4.5 C8 隔离）。

### 4.3 Unique（唯一性）

**文档含义**：数据集中的每条业务记录应具有唯一性，避免重复记录和不必要的数据冗余。

**第一层：业务主键唯一性（唯一性主判据）**

按数据语义，`ratings` 的业务主键是 **(UserID, MovieID)**，因为一次"用户对某电影的评分"在业务上应只有一条。

| 编号 | 检查项 | 判据 |
| --- | --- | --- |
| U1 | `ratings` 中 `(UserID, MovieID)` 不重复 | 分组计数，`count > 1` 即违规 |
| U2 | `movies` 中 `MovieID` 不重复 | 同上 |
| U3 | `users` 中 `UserID` 不重复 | 同上 |
| U4 | 完全重复行 | 整行字节级相同 |

**公式：**

```
Unique = 100 × (1 − |R_dup_pk| ÷ |R_total|)
```

**说明与实测结果（`rule-v2` 口径：必须区分两类重复）**

`rule-v2` 在唯一性维度上把两类问题分开统计与处置，因为它们的可解性完全不同：

| 类型 | 定义 | 能否确定真值 | 处置 |
| --- | --- | --- | --- |
| **完全重复行** | 整行字节级相同（**唯一性维度 U4**） | **能** —— 重复行之间没有任何信息差异 | **去重**：保留 1 条，其余移除，**信息不丢失** |
| **主键冲突** | 同一业务主键下 ≥2 条**字段级合法但取值不同**的记录 | **不能** —— 数据本身不含真值判据 | 见下方"冲突策略"，**未真正解决** |
| 主键重复（合计） | 同一业务主键出现 ≥2 条记录（含上面两类） | — | 唯一性维度按此计违规（U1–U3） |

| 检查项 | 主键重复（计分口径） | 其中"主键冲突" | 其中"完全重复行"（去重移除） |
| --- | --- | --- | --- |
| U1 `(UserID, MovieID)` 重复 | **4,815** 个主键 | **4,096** 个主键 | **55,166** 条 |
| U2 `movies.MovieID` 重复 | **495** 个主键 | **105** 个主键 | **252** 条 |
| U3 `users.UserID` 重复 | **789** 个主键 | **127** 个主键 | **321** 条 |
| U4 完全重复行 | — | — | 合计 **55,739** 条 |

- 唯一性得分：清洗前 `100 × (1 − (4,815+495+789) ÷ 1,161,652) = ` **99.4750**；清洗后 **100.0000**；
- `(UserID, MovieID)` 唯一组合数清洗前只有 **1,021,932**，小于结构合法行数 1,136,738，说明重复是**成片出现的注入数据**，不是零星错误；
- 唯一性维度清洗后满分，**但这只表示"主键不再重复"，不代表冲突已被修正** —— 4,328 个冲突主键计入未解决问题（见 6.4）。

**冲突策略（`rule-v2`，写入 `hadoop/config/rules.json` → `conflict_policy`）**

| 表 | 表性质 | 策略 | 理由 |
| --- | --- | --- | --- |
| `ratings` | 事实表 | **整组隔离**（4,096 个主键，涉及 8,192 条） | 评分是事件记录，没有其它表引用 `ratings`，隔离不会造成任何**引用断裂**，代价仅为数据量减少；反之若"任选一条保留"，实测 4,096 个冲突键中有 3,902 个会选中被注入的值，等于把可疑评分写进数据集。**不确定就不猜。** |
| `users` | 维表 | **保留一条**，其余移除 | `UserID` 被 `ratings` 引用，整条删除会让原本合法的评分变成**孤儿记录**，代价高于保留一条可疑值 |
| `movies` | 维表 | **保留一条**，其余移除 | 理由同 `users`：`MovieID` 被 `ratings` 引用 |

保留规则是确定性的（可复现）：优先无修复动作的记录 → 非空字段更多者 → 字节序最小者。

> **两类代价的对比（本方案的设计立场）**：维表"整条删除"的代价是**引用断裂**（合法评分失去可关联的属性），事实表"任选一条"的代价是**把可疑值当成真值写入**。前者可以用"标注未解决"来如实交代，后者无法在数据内部被发现，因此 `ratings` 选择整组隔离、维表选择保留一条，两类问题**全部计入未解决问题**。
>
> **保留一条 ≠ 已知真值**：与官方口径对照，`movies` 有 **48** 部、`users` 有 **87** 位保留下来的取值与官方不同 —— 足以说明"保留"只是可复现的确定性选择，不是修正。详见 6.4。
>
> 编号 U1 与 U4 的区别需在报告中说明：若同一用户在不同时间对同一电影评分（业务上可解释为"重复观看后再次评价"），U1 会判违规但 U4 不会。本轮实测两类同时存在，因此拆开统计。

### 4.4 Up-to-date（时效性）

**文档含义**：数据应足够新，能够反映所关注对象的当前状态。

**⚠️ 本维度最容易设计错误。** 若以"当前日期"为参照，则 2000–2003 年的数据全部不合格，而文档明确"数据年代较早并不必然属于错误"。因此本维度采用**两层设计**：

**第一层：时间可解释性（客观、可自动验证）**

| 编号 | 检查项 | 判据 |
| --- | --- | --- |
| D1 | `Timestamp` 可转为合理日期 | 能成功转换且落在 1970-01-01 之后 |
| D2 | `Timestamp` 落在数据集覆盖范围内 | 位于 2.2 实测 `[min, max]` 区间内 |
| D3 | 单位一致性 | 以**秒**为单位解释时落在 `[956703932, 1046454590]`；取值 `> 10¹¹` 视为**毫秒**（`rule-v2` 新增），整除 1000 换算后仍在该区间外则判违规 |

> `> 10¹¹` 这一毫秒判定阈值是本项目的**工程约定**（写入 `hadoop/config/rules.json` → `timestamp_ms_threshold`）。它能覆盖"秒被误写成毫秒"这一种单位混淆；若混淆方式更复杂（微秒、随机偏移），本规则不足以覆盖（见 6.3 第 8 条）。

```
Up-to-date_reliability = 100 × (1 − |R_violate_D1_D2_D3| ÷ |R_total|)
```

**第二层：时间新鲜度（参照 T2；T1/T2 已确定，本层已实现）**

```
freshness(r) = clamp( (t_r − T1) ÷ (T2 − T1), 0, 1 )
Up-to-date = 100 × (1 − 时间违规率) × mean( freshness(r) for r in R )
```

即 `Up-to-date = 第一层得分 × freshness 均值`。
时间不可解释的记录不会因其时间戳落在早期而获得高分。

**实测结果（`task_002`，清洗前后使用同一份程序、同一套阈值）**

| 项 | 清洗前 | 清洗后 |
| --- | --- | --- |
| 时间可解释记录 | 1,111,608 ÷ 1,150,241 = **96.6413%** | 996,113 ÷ 996,113 = **100%** |
| 第一层得分 | **96.6413** | **100.0000** |
| freshness 合计 | **346,333.83** | **211,334.83** |
| 参与计算记录数 | **1,131,112** | **996,113** |
| **freshness 均值** | **0.306197** | **0.212159** |
| **Up-to-date 得分** | `96.6413 × 0.306197` = **29.5905** | `100.0 × 0.212159` = **21.2159** |

**为什么清洗前反而"更高"（已核查，不是清洗引入的新问题）**

1. 清洗前有 **13,503 条毫秒时间戳**（如 `1009669227000`，按秒解释相当于公元三万年）——换算前它们的 `freshness` 被 clamp 到 **1**；
2. 注入记录中还有大量时间戳落在 `T2` 之后甚至 2100 年（`4102444800`），同样被 clamp 到 **1**。

这些"假的很新"的记录把清洗前均值抬到 **0.306197**；清洗把毫秒戳换算、把越界戳隔离之后，均值回落到 **0.212159**——这正是官方数据（`movielens-1m-v1`，官方口径对照值 1,000,209 条）的真实水平（**0.2154 量级**）。

**得分由 29.5905 下降至 21.2159（−8.3746）是合理的**：清洗前的 29.5905 是数据错误造成的假象，清洗后的 21.2159 才反映真实的时间分布。依据迭代一需求第 69 行"不要求所有维度的分数都提高，也不预设必须达到的分数"，本维度**保持原样上报**，不得为了"分数好看"而调整公式或权重。

**freshness 分布（T1/T2 为分位数切点的必然结果，清洗后 996,113 条）**

| 区间 | 条件 | 条数 | 精确占比 | freshness |
| --- | --- | --- | --- | --- |
| 训练期 | `t ≤ T1`（clamp 下界） | 700,148 | 70.29% | 0 |
| 验证期 | `T1 < t ≤ T2` | 150,031 | 15.06% | 0 ~ 1 线性 |
| 测试期 | `t > T2`（clamp 上界） | 145,934 | 14.65% | 1 |
| **合计** | — | **996,113** | 100% | — |

> 与 2.4 节的划分表是同一组数据。测试期比官方口径少 4,096 条的原因见 2.4 节。

> ⚠️ **该维度得分（21.2159）明显低于其他四维，这不是缺陷，必须解释清楚。**
>
> 因为 T1/T2 按分位数确定，**70% 的记录必然落在 T1 之前**，其 freshness 被
> clamp 为 0。均值 0.2122 的含义是"整体数据窗口的新近程度约 21.2%"，
> 是对时间分布的客观描述，**不是"质量差"的判据**。
>
> 依据 `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 51 行：
> "数据年代较早并不必然属于错误"。
>
> 因此本维度**不得单独作为数据质量的结论**，在汇报与前端展示中必须配合
> 上述说明使用。这也是本维度权重被设为 **0.10**（五维最低档）的原因。

**本方案明确声明：**

- 不将"评分发生在 2001 年"视为质量缺陷。
- 时效性得分的含义是"**在数据集自身的观测窗口内，数据的时间分布与新近程度**"，**不是**"数据相对今天的过时程度"。
- 若评价目标要求"数据必须反映当前状态"，则本数据集（2000–2003）在该意义上**完全不满足** —— 这一事实本方案不回避。
- 若 B/C 认为该维度难以支撑结论，可**降级为说明性指标**（只报告 D1–D3 与时间分布直方图，不给单一分数），并在报告中标注理由。

### 4.5 Consistent（一致性）

**文档含义**：数据元素的类型、格式和含义应一致、清晰，不同记录及数据表之间不应相互矛盾，例如日期格式和单位是否统一。

本维度分三类检查，本轮实测得分 **96.7995 → 99.9249**，是产生真实改善的维度之一——但改善中有 4,328 个主键冲突只是"被隔离"或"被确定性选择"，**不是真正解决**（见 4.3）。

**（1）跨表引用完整性（含"跨表数据不一致"）**

| 编号 | 检查项 | 判据 |
| --- | --- | --- |
| C1 | `ratings.UserID` 在 `users` 中存在 | 反连接（anti-join）为空 |
| C2 | `ratings.MovieID` 在 `movies` 中存在 | 反连接为空 |
| C3 | `ratings` 中标识符落在 `ml-1m` 的取值域内（`rule-v2` 新增） | `UserID` ∈ **[1, 6040]**、`MovieID` ∈ **[1, 3952]** |

```
C_ref = 100 × (1 − (|V_C1| + |V_C2|) ÷ (|ratings| × 2))
```

> **C3 与 C1/C2 是两项不同的检查，不能互相替代**：C3 是**域校验**（只需单表即可判定，超出取值域的 ID 必然是构造记录），C1/C2 是**引用完整性**（需要 `ratings` 与维表做 join）。实测中越界的 ID 必然同时造成引用断裂，因此两者会命中同一批记录——这是**有意保留的双重取证**，避免"取值域被放宽后引用完整性检查同时失效"。

**实测结果：**

| 项 | 清洗前 | 清洗后 |
| --- | --- | --- |
| C1 `ratings.UserID` 悬空引用 | **10,502** 条 | **2,994** 条（涉及 15 个 `UserID`） |
| C2 `ratings.MovieID` 悬空引用 | **10,502** 条 | **0** |
| C3 超出取值域（`UserID` / `MovieID`） | **各 10,502** 条 | **0 / 0** |
| `C_ref` | **99.0870** | **99.8497** |

**（2）表内值域与格式一致性**

| 编号 | 检查项 | 判据 |
| --- | --- | --- |
| C4 | 同一 `MovieID` 只有一种 `Title` | 分组后 `distinct Title` 数 = 1 |
| C5 | 同一 `MovieID` 只有一种 `Genres` | 分组后 `distinct Genres` 数 = 1 |
| C6 | 同一 `UserID` 只有一组属性 | 分组后 `Gender/Age/Occupation/Zip` 各自 `distinct` 数 = 1 |
| C7 | `Genres` 内部无重复项、无空项 | 按 `\|` 切分后无重复、无空串（如 `Drama\|Drama`、`Drama\|`）。**实测 0 条违规** |
| C8 | `Genres` 各项均属文档规定类别，且 `Genres` 非空 | 属于固定的 **18** 类标准类别；出现未识别类别或 `Genres` 为空 → **隔离** |
| C9 | `Zip-code` 格式一致 | 全部为 5 位数字且**保留前导零**（未被读成数值）。**实测 279 条不合规**，明细见下 |
| C10 | `Title` 无首尾空白、无异常控制字符 | 未匹配 `^\s\|\s$` 及非法字符。**实测 47 条含首尾空白、104 条含非 ASCII 特殊字符**，见下 |

> **C4/C5/C6 的本质是主键冲突，不是格式问题**：同一主键对应多个不同取值时，数据本身无法判定哪个为真值，因此这三项对应的记录在 `rule-v2` 中按 **4.3 的冲突策略**处置，并计入**未解决问题**，不得表述为"已修正"。实测：`movies` 同一 `MovieID` 多变体 **384** 个主键、`users` 同一 `UserID` 属性冲突 **608** 个主键（清洗后均为 0，但不代表真值已确认）。

**C8 的类别集合（18 类标准类别，按字典序）：**

```text
Action, Adventure, Animation, Children's, Comedy, Crime, Documentary,
Drama, Fantasy, Film-Noir, Horror, Musical, Mystery, Romance, Sci-Fi,
Thriller, War, Western
```

> **实测（清洗前）：** 出现 **1 个未识别类别**（注入的 `UnknownGenre`），命中 **174** 条记录；另有 **50** 条 `Genres` 为空。两类合计 **224** 条在 `rule-v2` 中一律**隔离**（未被识别说明无法确定应映射到哪个标准类别；`Genres` 为空则类型信息完全缺失且无法由其它字段推导）。清洗后未识别类别 **0**、空 `Genres` **0**，实际使用的类别为 **18** 类。
>
> 注意 `Genres` 在 4.2 中被定义为**可选字段**，因此这 224 条属"无法验证"而非"记录错误"——隔离是**取证取向**的选择，不是对记录真实性的判定。

**C9 的不合规明细（实测共 279 条，占 6,946 的 4.02%）：**

| 形态 | 条数 | 样例 | 判定 |

| 含非数字 | **45** | `ABCDE` | 无法确定正确值，**隔离** |
| 空值 | **22** | — | 同上 |
| 2 位数字 | **45** | `05` | 同上 |
| 6 位数字 | **13** | `495321` | 无法解释的多余数字，**隔离**而非擅自截断 |
| 7 位数字 | **3** | `5849574` | 同上 |
| 9 位数字 | **1** | `193122042` | 同上，疑似加拿大邮编或输入错误 |

| 前导零（5 位，`0xxxx`） | **733 → 661** | `06810` | **不是问题**，只要按字符串读取即可保留；若被当作数值读入会丢失前导零，这正是 C9 要防的陷阱 |

**C10 的实测说明：**

- **104** 条标题含有 ISO-8859-1 范围内的特殊字符（清洗后 **74** 条），例如 `Misérables, Les (1995)`、`Metisse (Café au Lait) (1993)`、`Eighth Day, The (Le Huitième jour ) (1996)`。**这些不是错误数据**，而是**编码处理是否正确**的判据：以 ISO-8859-1 正确读取则显示正常，误用 UTF-8 读取会出现乱码。本轮将其作为"编码一致性"的检查项，处置为 `keep`。
- **47** 条标题首尾存在空白字符，属可安全去除的**修复**项，清洗后为 0。

```
C_format = 100 × (1 − Σ_check |V_check| ÷ Σ_check |R_check|)
```

**实测结果：** `C_format` 清洗前 **94.5121**、清洗后 **100.0000**（同 ID 多变体 384 / 608、未识别或空 `Genres` 224、标题首尾空白 47、`Zip-code` 不合规 279 等项全部归零）。

**（3）维度合成**

```
Consistent = 0.5 × C_ref + 0.5 × C_format
```

权重 0.5/0.5 的理由：跨表引用错误只影响 `ratings`，格式错误散布三表；各占一半可避免任一类被另一方稀释。

**实测结果：** 清洗前 `0.5 × 99.0870 + 0.5 × 94.5121` = **96.7995**；清洗后 `0.5 × 99.8497 + 0.5 × 100.0000` = **99.9249**。

> 清洗后未能满分，原因有两个，都是**如实反映**而非计算问题：① 2,994 条因维表隔离产生的孤儿评分（C1）；② 4,328 个冲突主键的取值未经真值确认（C4/C5/C6，见 4.3）。

> **本方案声明**：`movies.Genres` 与 `users.Occupation` 之间**不存在语义关联**，因此不做跨表值域交叉校验。`Zip-code` 与 `Occupation` 的地理一致性**无法验证**（数据集不含地区真值），见第 6 节。

## 5. 汇总与对比口径

### 5.1 综合分

```
Overall = 0.25 × Accurate
        + 0.25 × Complete
        + 0.15 × Unique
        + 0.10 × Up-to-date
        + 0.25 × Consistent
```

**本轮实测五维对照（`task_002`，同一套程序、同一套阈值，仅输入数据集不同）：**

| 维度 | 清洗前 | 清洗后 | 变化 | 主要来源 |
| --- | --- | --- | --- | --- |
| Accurate 准确性 | **97.7423** | **99.9506** | **+2.2083** | 非法字段值被修复或隔离（余 23 条缺年份标题） |
| Complete 完整性 | **97.9906** | **100.0000** | **+2.0094** | 必需字段缺失的记录被隔离 |
| Unique 唯一性 | **99.4750** | **100.0000** | **+0.5250** | 完全重复行去重、主键冲突按 4.3 处置 |
| Up-to-date 时效性 | **29.5905** | **21.2159** | **−8.3746** | ⚠️ **下降且合理**，异常时间戳被换算/隔离，见 4.4 |
| Consistent 一致性 | **96.7995** | **99.9249** | **+3.1254** | 悬空引用与格式冲突被处置（余 4,328 个冲突主键、2,994 条孤儿评分） |
| **综合分** | **91.0134** | **92.0905** | **+1.0771** | 加权平均，权重见下 |

> **本方案明确不要求所有维度的分数都提高**（迭代一需求第 69 行）。Up-to-date 的下降是清洗把"被异常时间戳抬高的假分数"还原为真实水平所致（推导见 4.4），**不得**为了制造全面改善而修改公式、权重或阈值；也不得因为某一维度未提高就把数据改回去。

**权重设计依据：**

| 维度 | 权重 | 理由 |
| --- | --- | --- |
| Accurate | 0.25 | 值域合法性是后续一切分析的基础，权重最高档 |
| Complete | 0.25 | 关键字段缺失会直接使记录不可用，权重最高档 |
| Consistent | 0.25 | 跨表关联断裂会使整条记录失去分析价值，权重最高档 |
| Unique | 0.15 | 重复会污染统计结果，但本轮的重复可通过去重与冲突处置收敛，取次高档 |
| Up-to-date | 0.10 | 本数据集为历史快照且 90% 以上评分集中在 2000 年，该维度衡量的是"数据窗口内的新近程度"而非错误率，区分度有限，取低档 |

> 是否设置综合分**由学生决定**（迭代一需求第 55 行）。本方案**设置综合分用于趋势概览**，但规定：**汇报与前端展示必须以五维明细为主，综合分不得替代明细**，因为加权会掩盖"某维度未改善"的事实。

### 5.2 同一口径的实现要求

Before 与 After 两次评分**必须调用同一份评分程序、同一套阈值、同一套权重**，仅输入数据集不同（依据：迭代一需求第 69 行）。

**实现约束：**

- 评分参数（阈值、权重、类别集合、冲突策略）集中在 `hadoop/config/` 的配置文件中，不硬编码。
- Before 与 After 使用**同一份配置文件**，程序记录配置内容的哈希值作为 `rule_version`；本轮为 **`rule-v2`**，输入为 `movielens-1m-v2`、输出为 `movielens-1m-v2-clean-v1`。
- After 的评分对象是**清洗后的主数据集**，被隔离的数据**不计入** After 的分母，但必须在报告中被单独统计。

## 6. 适用范围、无法验证的情况与局限

> 本节对应迭代一需求第 108 行"说明学生设计的评价方法、**适用范围和局限**；**未完成、无法评价和未验证的情况应清楚标注**"，必须随评分结果一并展示。

### 6.1 适用范围

本方案适用于 MovieLens 1M 三个 `.dat` 文件的**结构与格式质量评估**，以及清洗前后质量的**相对比较**。不适用于评价推荐算法的效果，也不用于评价数据的商业价值。

### 6.2 明确无法验证的情况

| 事项 | 为什么无法验证 |
| --- | --- |
| **用户属性真实性** | `users.dat` 的人口属性由用户自愿填写，GroupLens 未核验（引言第 67 行）。格式正确**不能**证明内容真实。 |
| **评分真实性（是否真实偏好）** | 数据集不含行为真值，"用户评了 5 分"是否反映真实喜好无法从数据判定。 |
| **`Zip-code` 与 `Occupation`/地区的一致性** | 缺少地区真值参照，无法交叉验证。 |
| **"用户名"层面的同一人判定** | 用户标识已匿名化，无法判断不同 ID 是否属于同一自然人。 |
| **同名电影是否为同一部** | 不同 `MovieID` 可能有相同标题（如翻拍），仅凭标题无法判定，需外部知识库。 |
| **时间戳的时区正确性** | 数据集未声明时区，本方案统一按 UTC 解释，可能存在固定偏移。 |
| **"评分行为分布异常"是否属于质量问题** | 文档第 33 行指出该现象需结合数据背景判断。本方案**不**将其计入准确性扣分，仅作为观察输出。 |

### 6.3 方法本身的局限

1. **合法性 ≠ 准确性。** 本方案的 Accurate 维度实际衡量的是"字段值合法率"，不能证明"值真实反映现实"。这是文档第 67 行提出的思考题"格式正确是否足以证明真实性"的答案：**不足以**。
2. **微平均对字段数敏感。** 4.1 的微平均使字段较多的表影响更大；已通过"每字段一次机会"缓解，但未做表级加权。
3. **Up-to-date 参照系是相对的。** 以 T1/T2 为参照衡量的是"数据集窗口内的新近程度"，**不是**绝对时效性。若应用场景要求"数据必须反映当前状态"，则本数据集（2000–2003）**在该意义上完全不满足**，本方案不回避这一事实。
4. **完整性分级含主观判断。** 4.2 中"必需字段"的划分基于业务可用性推理，属设计决策而非客观事实，不同划分会得到不同得分。
5. **权重为设计选择，非测量结果。** 5.1 的权重反映本团队对该场景重要性的判断，改变权重会改变综合分排序。
6. **得分提升不等于问题全部解决。** 经"隔离"处置的记录会提高 After 得分，但问题只是被移出主数据集，并未被修正（文档第 91 行）。
7. **0–100 不是概率或百分比质量。** 得分不表示"数据有 X% 是正确的"这一绝对意义。
8. **毫秒时间戳的判定阈值是工程约定。** 4.4 D3 采用"`> 10¹¹` 视为毫秒"，这只覆盖"秒被误写成毫秒"这一种单位混淆；若混淆方式更复杂（微秒、随机偏移），本规则不足以覆盖。
9. **冲突处置是折中，不是修正。** `ratings` 整组隔离会损失 4,096 条合法评分（占官方口径的 0.41%），维表保留一条会留下 48 / 87 条未经确认的取值；两种代价都已在 4.3 与 6.4 量化，**不得**据此声称"冲突已解决"。

## 8. 附：可复现的验证命令

以下命令用于在本地快速复核本文档的关键结论。清洗前数据在 `~/data/ml-1m-v2`（校验和见 `data/DATASETS.md`），清洗后数据在 `hadoop/output/clean/`。

```bash
# ===== 2. 规模与时间边界 =====

# 2.1 规模核对（清洗前，期望 1150241 / 4465 / 6946）
wc -l ratings.dat movies.dat users.dat

# 2.1 规模核对（清洗后，期望 996113 / 3883 / 6025）
wc -l hadoop/output/clean/ratings.dat hadoop/output/clean/movies.dat hadoop/output/clean/users.dat

# 2.2 时间范围（期望 956703932 / 1046454590）
#   ⚠️ v2 含非数字戳、毫秒戳与越界戳，必须先过滤出"秒单位且在区间内"的记录，
#      直接对 $4 取 min/max 会被非数字值或毫秒值带偏。
awk -F'::' '$4 ~ /^[0-9]+$/ {t=$4+0;
  if(t>=956703932 && t<=1046454590){ if(n++==0) min=t; if(t<min) min=t; if(t>max) max=t }}
  END{print min, max}' ratings.dat

# ===== 4.0 解析层 =====

# 4.0 P3 结构异常（清洗前期望 ratings 13503 / movies 70 / users 108；清洗后均 0）
awk -F'::' 'NF!=4{n++} END{print n+0}' ratings.dat
awk -F'::' 'NF!=3{n++} END{print n+0}' movies.dat
awk -F'::' 'NF!=5{n++} END{print n+0}' users.dat

# ===== 4.1 Accurate =====

# 4.1 A1/A2 标识符非正整数（清洗前期望各 9377；清洗后 0）
awk -F'::' 'NF==4 && $1 !~ /^[1-9][0-9]*$/ {n++} END{print n+0}' ratings.dat
awk -F'::' 'NF==4 && $2 !~ /^[1-9][0-9]*$/ {n++} END{print n+0}' ratings.dat

# 4.1 A3 评分非法（清洗前期望 49886，取值含 0/6/3.5/five/空；清洗后 0）
awk -F'::' 'NF==4 && $3 !~ /^[1-5]$/ {n++} END{print n+0}' ratings.dat

# 4.1 A4 毫秒时间戳（清洗前期望 13503；清洗后 0）
awk -F'::' 'NF==4 && $4 ~ /^[0-9]+$/ && $4+0>100000000000 {n++} END{print n+0}' ratings.dat

# 4.1 A4 落在合法区间内的时间戳（清洗前期望 1111608；清洗后 996113）
awk -F'::' 'NF==4 && $4 ~ /^[0-9]+$/ && $4+0>=956703932 && $4+0<=1046454590 {n++} END{print n+0}' ratings.dat

# ===== 4.3 Unique =====

# 4.3 U1 (UserID,MovieID) 唯一组合数（清洗前期望 1021932，小于结构合法行数 1136738；清洗后 996113）
awk -F'::' 'NF==4 {print $1"::"$2}' ratings.dat | sort -u | wc -l

# 4.3 U4 完全重复行（清洗前期望 ratings 55166 / movies 252 / users 321；清洗后均 0）
sort ratings.dat | uniq -d | wc -l
sort movies.dat  | uniq -d | wc -l
sort users.dat   | uniq -d | wc -l

# ===== 4.4 Up-to-date =====

# 4.4 freshness 均值（清洗后期望 0.212159 / 996113）
#   清洗前的 0.306197 / 1131112 见 reports/quality-report/task_002.json → score_details.up_to_date
awk -F'::' 'BEGIN{T1=974862386; T2=976422054}
  {t=$4+0; s+=(t<=T1)?0:((t>=T2)?1:(t-T1)/(T2-T1)); n++}
  END{printf "%.6f %d\n", s/n, n}' hadoop/output/clean/ratings.dat

# ===== 4.5 Consistent =====

# 4.5 C1/C2 跨表引用完整性（清洗前期望两个 10502；清洗后期望 2994 / 0）
awk -F'::' '{print $1}' ratings.dat | sort -u > /tmp/ru.txt
awk -F'::' '{print $1}' users.dat   | sort -u > /tmp/uu.txt
comm -23 /tmp/ru.txt /tmp/uu.txt | wc -l     # ratings 中 users 不存在的 UserID

awk -F'::' '{print $2}' ratings.dat | sort -u > /tmp/rm.txt
awk -F'::' '{print $1}' movies.dat  | sort -u > /tmp/um.txt
comm -23 /tmp/rm.txt /tmp/um.txt | wc -l     # ratings 中 movies 不存在的 MovieID

# 4.5 C9 Zip-code 不合规条数（清洗前期望 279；清洗后 0）
awk -F'::' '$5 !~ /^[0-9]{5}$/ {n++} END{print n+0}' users.dat

# 4.5 C9 Zip-code 前导零条数（清洗前期望 733、清洗后期望 661，属正常）
#   用 ^0[0-9]{4}$ 限定"5 位且以 0 开头"；若写成 ^0，会把 6/7 位数字里的前导零
#   也计入，与 733 不是同一口径。
awk -F'::' '$5 ~ /^0[0-9]{4}$/ {n++} END{print n+0}' users.dat

# 4.5 C7 Genres 内部重复项条数（期望 0）
awk -F'::' '{n=split($3,a,"|"); delete s; for(i=1;i<=n;i++){ if(a[i] in s){bad++; break} s[a[i]]=1 }} END{print bad+0}' movies.dat

# 4.5 C8 Genres 未识别类别条数（清洗前期望 174、清洗后 0）
awk -F'::' '{n=split($3,a,"|"); for(i=1;i<=n;i++) if(a[i]=="UnknownGenre"){bad++; break}} END{print bad+0}' movies.dat

# 4.5 C8 Genres 为空条数（清洗前期望 50、清洗后 0）
awk -F'::' 'NF==3 && $3=="" {n++} END{print n+0}' movies.dat

# 4.5 C8 Genres 实际使用的类别（清洗前期望 19 类 = 18 标准 + UnknownGenre；清洗后 18 类）
awk -F'::' '{n=split($3,a,"|"); for(i=1;i<=n;i++) print a[i]}' movies.dat | sort -u

# 4.5 C10 Title 含非 ASCII 特殊字符的行数（清洗前期望 104、清洗后 74）
#   ⚠️ movies.dat 是 ISO-8859-1 编码：含非 ASCII 字节时 grep 会把它判定为
#      「二进制文件」并改变行为（实测 grep -v 会把 3,883 行丢成 3,833 行），
#      因此本项一律用 awk，不要用 grep。
awk '/[^\x00-\x7F]/' movies.dat | wc -l

# 4.5 C10 Title 含首尾空白条数（清洗前期望 47、清洗后 0）
awk -F'::' '$2 ~ /^[[:space:]]|[[:space:]]$/ {n++} END{print n+0}' movies.dat

# 4.5 C6 同一 UserID 属性冲突（清洗前期望 608，对应 users_attr_multi_violations；清洗后 0）
awk -F'::' '{k=$1; v=$2"|"$3"|"$4"|"$5; if(k in seen){ if(seen[k]!=v) bad++ } else seen[k]=v} END{print bad+0}' users.dat

# ===== 4.1 A9/A10 movies 标题 =====

# A9 标题为空（清洗前期望 87、清洗后 0）
awk -F'::' '$2=="" {n++} END{print n+0}' movies.dat

# A10 缺结尾年份（清洗前期望 163，其中结构合法行 145；清洗后期望 23）
awk -F'::' '$2 !~ /\([0-9]{4}\)[[:space:]]*$/ {n++} END{print n+0}' movies.dat

# A10 年份越界（期望 0 / 0）
awk -F'::' 'match($2, /\(([0-9]{4})\)[[:space:]]*$/, m) { if (m[1]<1900 || m[1]>2003) n++ } END{print n+0}' movies.dat
```
