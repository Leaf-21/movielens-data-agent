## 1. 目的与依据

### 1.1 本文档解决什么问题

系统需要"清洗前后五维评分对比"，而对比要成立，前提是**有一套明确、可复现、清洗前后完全一致的评价口径**。本文档就是这套口径的定义：

- 每个维度的**含义**、**可计算指标**、**计算公式**
- 每个维度的**分值范围**与**权重**，以及是否设置综合分
- 本次评价**覆盖不了什么**（无法验证的情况与局限）

### 1.2 文档依据

| 要求 | 出处 |
| --- | --- |
| 五维含义由文档给出，具体指标/打分方法/分值范围/权重/是否设综合分**由学生自主设计** | `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 55 行 |

### 1.3 一条前置设计原则（重要）

- 本文档的指标**先定义、后测量**，不得在看到结果后回头调整公式或权重来制造"分数提升"。
- 若某维度清洗前后得分相同，**如实记录并解释原因**，不视为缺陷（依据：第 69 行）。
- 若某维度**无法有效评价**，标注为"不适用/证据不足"，不强行给分。

## 2. 评价对象与时间边界

### 2.1 数据集

MovieLens 1M（`ml-1m`），三个文件、无表头、`::` 分隔、ISO-8859-1 编码。

| 文件 | 字段 | 实测规模 | 必需字段 |
| --- | --- | --- | --- |
| `ratings.dat` | `UserID::MovieID::Rating::Timestamp` | 1,000,209 | 全部 4 个 |
| `movies.dat` | `MovieID::Title::Genres` | 3,883 | `MovieID`、`Title`（`Genres` 见 4.2） |
| `users.dat` | `UserID::Gender::Age::Occupation::Zip-code` | 6,040 | `UserID`（其余为属性，见 4.2） |

### 2.2 实测时间范围

| 项 | Unix 时间戳 | 日期 |
| --- | --- | --- |
| 最早评分 | 956703932 | 2000-04-25 |
| 最晚评分 | 1046454590 | 2003-02-28 |
| 跨度 | — | 1039 天（约 2.84 年） |

该范围与文档"2000 年加入 MovieLens 的用户、2003 年 2 月发布"的描述一致。

### 2.3 实测质量概况（迭代一分析结论）

对原始数据完成一遍完整检查后，得到如下结论。**这一节是清洗规则设计的依据。**

**（a）结构完整性：完全合格**

| 检查项 | 结果 |
| --- | --- |
| `ratings.dat` 字段数 ≠ 4 | **0** |
| `users.dat` 字段数 ≠ 5 | **0** |
| `movies.dat` 字段数 ≠ 3 | **0** |
| 评分越界（<1 或 >5）或非整数 | **0** |
| 完全重复行 | **0** |
| `(UserID, MovieID)` 重复 | **0**（唯一组合数 = 1,000,209 = 总行数） |
| `ratings.UserID` 在 `users` 中不存在 | **0** |
| `ratings.MovieID` 在 `movies` 中不存在 | **0** |
| 同一 `MovieID` 对应多个 `Title`/`Genres` | **0** |
| 同一 `UserID` 对应冲突属性 | **0** |
| `Title` 缺少结尾年份 `(YYYY)` | **0** |
| `Genres` 内部重复项或空项 | **0** |
| `Genres` 出现未识别类别 | **0**（实测 18 类，见 4.5 C8） |

**（b）真正存在的问题：只有以下三项**

| 问题 | 规模 | 说明 |
| --- | --- | --- |
| **`Title` 含 ISO-8859-1 特殊字符** | **50 条** | 如 `Misérables, Les (1995)`、`Metisse (Café au Lait) (1993)`、`Eighth Day, The (Le Huitième jour ) (1996)`。若以 UTF-8 读取会变成乱码，属于典型的**编码处理问题** |
| **`Zip-code` 非标准 5 位格式** | **81 条** | 明细见 4.5 C9：ZIP+4（66 条）、6 位（11 条）、7 位（3 条）、9 位（1 条） |
| **`Genres` 电影类型数分布不均** | — | 单类型 2025 部，最多 6 类型（仅 1 部）。属正常业务现象，**不作为质量问题** |

**（c）由此得出的设计结论**

1. **"脏数据类"问题（字段错、值越界、重复、关联断裂）在本数据集中并不存在。** 这意味着按常见思路设计的去重、越界修复规则，运行结果将是 **0 条**。
2. **真实的可改进点集中在"格式与编码一致性"**，即 **Accurate 的 A9–A10、Consistent 的 C9** 等项。
3. 因此本方案的预期是：**部分维度清洗前后得分相同**。依据本文档 1.3 节与迭代一需求第 69 行，这属于**如实报告的真实结论**，不得通过人为降低 Before 分数来制造改善。

### 2.4 T1 / T2 时间边界 ⚠️ 待 B/C 确认

依据 `docs/引言_项目总体要求与汇报安排.md` 第 11 行与 `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 13 行，迭代一需统一确定 `T1/T2`，后续迭代不得混用。

| 边界 | 建议取值 | Unix 时间戳 | 含义 | 数据占比 |
| --- | --- | --- | --- | --- |
| **T1** | **2000-11-22** | **974862386** | 训练期截止时间 | 70.0% |
| **T2** | **2000-12-10** | **976422054** | 验证期截止时间 | 15.0% |
| 测试期 | `> T2` | — | 测试数据位于 T2 之后 | 15.0% |

切分方法：**按 `ratings.Timestamp` 的实际分位数取 70% 与 85% 位置**（不是按时间跨度等分）。

**实测划分效果：**

| 集合 | 条件 | 条数 | 精确占比 |
| --- | --- | --- | --- |
| 训练期 | `t ≤ T1`（即 `freshness = 0`） | 700,144 | 69.9998% |
| 验证期 | `T1 < t ≤ T2`（`freshness` 线性区） | 150,035 | 15.0004% |
| 测试期 | `t > T2`（即 `freshness = 1`） | 150,030 | 14.9999% |
| **合计** | — | **1,000,209** | 100% |

> **⚠️ 关于边界条件（容易数错）**
>
> 上面的条数按**分组后的 `freshness` 值**划分，与程序实现完全一致：
>
> ```
> relaxed = clamp((t − T1) / (T2 − T1), 0, 1)
> freshness == 0  -> 训练期
> freshness == 1  -> 测试期
> 其余            -> 验证期
> ```
>
> 有 4 条记录的 `Timestamp` **恰好等于 T1**（974862386 秒）。它们的 `freshness` 计算为
> `(t−T1)/span = 0`，属于**验证期的线性区**但取值为 0。
> 因此若改用 `t <= T1` 这种严格不等式统计，会得到 700,148 / 150,031 / 150,030 ——
> 与上表差 4 条。**上表才是与 `freshness` 计算逻辑一致的数值。**
>
> 占比之和显示为 99.9999% 是四舍五入误差，不是数据缺失。

> **⚠️ 必须使用 epoch 值而非日期。** 按日期午夜切分与按分位数精确切分的结果相差约 0.5 个百分点，
> 后续迭代只有使用 epoch 才能复现同一划分。程序输出中同时提供 `T1`/`T2`（日期）与 `T1_epoch`/`T2_epoch`。

**❌ 一个已被否决的方案（记录在案，避免重犯）：**

最初曾按「时间跨度的 70%/85% 位置」提出 `T1=2002-04-23`、`T2=2002-09-25`。该方案**错误**，原因是假设了数据在时间上均匀分布，而实际数据 **90.4% 集中在 2000 年**。实测后果：

| 集合 | 条数 | 占比 |
| --- | --- | --- |
| 训练期 | 983,130 | **98.29%** |
| 验证期 | 9,451 | 0.94% |
| **测试期** | **7,628** | **0.76%** |
| **合计** | **1,000,209** | 100% |

> **统计口径说明（便于复核）**：上表的条数按该方案的**日期取午夜 UTC** 计算，即
> `T1 = 1019520000`（2002-04-23 00:00 UTC）、`T2 = 1032912000`（2002-09-25 00:00 UTC）。
> 若改用「时间跨度的 70%/85% 位置」的精确 epoch，会得到 9,454 / 7,625 —— 与上表差 3 条，
> **差异来自边界口径而非数据**。两种口径都能说明同一结论（测试集远不足以支撑后续迭代），
> 本表采用与文档中给出的日期字面值一致的口径。

测试集仅 7,628 条（占 0.76%），不足以支撑迭代二的分类/聚类评估与迭代三的图分析。详见 `reports/quality-report/data-analysis-report.md` 第 4.2、4.3 节。

> **⚠️ 必须澄清的语义（关系到整套设计是否自相矛盾）**
>
> `T1/T2` **不是"数据有效期的截断线"**，不能因为"某条评分发生在 2001 年"就判定它"不新鲜"或把它当作清洗对象删除。
> 依据：`docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 51 行明确"**数据年代较早并不必然属于错误**"。
>
> `T1/T2` 的真实用途有两个：
> 1. 供**后续迭代**划分训练/验证/测试窗口（迭代二训练分类器需用）；
> 2. 作为本文档 **Up-to-date 维度的参照基准**（用"距 T2 的时间距离"衡量，而非"距今天"）。

## 3. 总体设计思路

### 3.1 评分层级

```
字段级检查  →  表级（文件级）率值  →  维度得分（0–100）  →  五维汇总
```

每个维度得分统一映射到 **0–100**，便于对比与展示。

### 3.2 为什么采用"违规率扣分"而非"直接给分"

采用 `得分 = 100 × (1 − 违规记录数 ÷ 适用记录总数)` 的形式，理由：

1. **可解释**：得分直接对应"多少条数据有问题"，Agent 能据此生成人类可读的解释。
2. **可比较**：清洗前后分母可能变化，因此分母分别取各自表的总记录数，并在报告中同时给出绝对条数。
3. **可复现**：公式只依赖原始数据与规则，不依赖人工判断。

### 3.3 与清洗处置的对应关系

| 处置方式 | 含义 | 对得分的影响 |
| --- | --- | --- |
| **修复** | 能确定正确值并改回 | 该违规项在 After 中消失，得分提升 |
| **去重** | 完全重复的业务记录 | 记录数减少，得分提升 |
| **隔离** | 疑似错误但无法确证，移出主数据集 | 记录数减少，得分提升（需在报告中说明是"隔离"而非"修正"） |
| **删除** | 确定无意义且不可恢复 | 记录数减少，得分提升 |

> 依据 `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 91 行：**避免将删除或隔离记录直接表述为"问题已修复"**。因此每个统计口径都必须**分别输出** `fixed_count` / `deduplicated_count` / `isolated_count`。

## 4. 五维指标定义

以下 `R` 表示适用记录集合，`|R|` 为其容量，`V` 为违规记录集合。所有维度最终得分域为 **[0, 100]**。

---

### 4.1 Accurate（准确性）

**文档含义**：数据的值应当真实反映现实世界的情况，避免错误或失真的信息。

**可评价部分**：字段值的**合法性**（是否落在文档规定的取值域内）。这是本轮唯一可自动验证的准确性层面。

| 编号 | 检查项 | 判据 | 适用范围 |
| --- | --- | --- | --- |
| A1 | `UserID` 为正整数 | 匹配 `^[1-9][0-9]*$` | ratings、users |
| A2 | `MovieID` 为正整数 | 匹配 `^[1-9][0-9]*$` | ratings、movies |
| A3 | `Rating` 为 1–5 的整数 | 匹配 `^[1-5]$` | ratings |
| A4 | `Timestamp` 为可解释的正整数 | 匹配 `^[0-9]+$` 且落在 2.2 实测范围内 | ratings |
| A5 | `Gender` 属于 `{M, F}` | 集合成员判定 | users |
| A6 | `Age` 属于 `{1,18,25,35,45,50,56}` | 集合成员判定 | users |
| A7 | `Occupation` 为 0–20 的整数 | 匹配 `^(1[0-9]|[0-9])$` 且 ≤ 20 | users |
| A8 | `Zip-code` 形如 5 位数字 | 匹配 `^[0-9]{5}$` | users |
| A9 | `Title` 非空 | 去除首尾空白后长度 > 0 | movies |
| A10 | `Title` 结尾含同年份 `(YYYY)` | 匹配 `\((\d{4})\)\s*$` 且年份在 1900–2003 | movies |

**公式：**

```
Accurate = 100 × (1 − Σ_check |V_check| ÷ Σ_check |R_check|)
```

即对所有检查项做**微平均**（每个字段一次机会），避免字段数多的表主导整体得分。

**实测结果（对应于第 2.3 节）：** 除 A8 外，A1–A7、A9、A10 的违规数均为 **0**。

| 检查项 | 实测违规数 | 说明 |
| --- | --- | --- |
| A1–A3、A5–A7 | 0 | `Gender` 实测仅 `M`(4331)/`F`(1709)；`Age` 实测仅 7 个规定编码；`Occupation` 实测 0–20 |
| A4 | 0 | 时间戳全部落在 2.2 的实测区间内 |
| A8 | **81** | `Zip-code` 非 5 位格式（明细见 4.5 C9） |
| A9、A10 | 0 | 全部记录标题非空且以 `(YYYY)` 结尾，年份均在 1900–2003 内 |

> **说明**：A1–A10 验证的是"值是否合法"，**不能证明值是否真实**。例如 `users.dat` 的人口属性由用户自愿填写且 GroupLens 未核验（`docs/引言_项目总体要求与汇报安排.md` 第 67 行），格式完全正确的 `Zip-code` 仍可能是错的。该局限见第 6 节。
>
> **同时注意 A8 与 C9 的关系**：两者检查的是同一字段，但归属维度不同 —— A8 判"值是否合法"（准确性），C9 判"格式是否统一"（一致性）。同一问题在两维各计一次是**有意设计**，因为该字段同时反映两个质量属性；若 B/C 认为构成重复计分，可将 A8 移出准确性维度（见 6.4）。

---

### 4.2 Complete（完整性）

**文档含义**：衡量业务所必需的数据是否完整，例如不能缺失的字段是否存在空值。

**关键问题**：哪些字段是"必需"的？本方案分级定义：

| 级别 | 字段 | 理由 |
| --- | --- | --- |
| **必需（缺失即违规）** | ratings：全部 4 字段；users：`UserID`；movies：`MovieID`、`Title` | 缺任一则记录无法定位或无法参与下游分析 |
| **属性（缺失单列统计，不计入扣分）** | users：`Gender`、`Age`、`Occupation`、`Zip-code` | 属于自愿填写的画像信息，缺失反映"信息不足"而非"数据错误" |
| **可选** | movies：`Genres` | 缺失不影响记录唯一性，仅影响类型维度分析 |

**⚠️ 该分级是本文档的一个设计决策**，依据 `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 51 行"应区分真正的数据错误、**信息不足**和正常的业务现象"。把"用户没填邮编"算作数据错误会系统性低估数据质量。

**公式：**

```
Complete = 100 × (1 − |R_missing_required| ÷ |R_total|)
```

其中 `R_missing_required` 为"任一必需字段为空/全空白/含缺失标记（如 `NA`、`NULL`、`?`、空串）"的记录集合。

**同时输出**（不计入得分，但写入报告，供 Agent 解释）：

```
OptionalFillRate(Zip-code)  = 非空 Zip-code 记录数 ÷ users 总记录数
OptionalFillRate(Genres)    = 非空 Genres 记录数   ÷ movies 总记录数
```

### 4.3 Unique（唯一性）

**文档含义**：数据集中的每条业务记录应具有唯一性，避免重复记录和不必要的数据冗余。

**第一层：业务主键唯一性（唯一性主判据）**

按数据语义，`ratings` 的业务主键是 **(UserID, MovieID)**，因为一次"用户对某电影的评分"在业务上应只有一条。

| 编号 | 检查项 | 判据 |
| --- | --- | --- |
| U1 | `ratings` 中 `(UserID, MovieID)` 不重复 | 分组计数，`count > 1` 即违规 |
| U2 | `movies` 中 `MovieID` 不重复 | 同上 |
| U3 | `users` 中 `UserID` 不重复 | 同上 |
| U4 | 完全重复行 | 整行字节级相同 |

**公式：**

```
Unique = 100 × (1 − |R_dup_pk| ÷ |R_total|)
```

**说明与实测结果**：

| 检查项 | 实测违规数 |
| --- | --- |
| U1 `(UserID, MovieID)` 重复 | **0**（唯一组合数 = 1,000,209 = 总行数） |
| U2 `movies.MovieID` 重复 | **0** |
| U3 `users.UserID` 重复 | **0** |
| U4 完全重复行 | **0** |

**因此唯一性维度在清洗前后都将得到 100.0 分。** 这属于"原始数据本身干净"的真实结论，按本文档 1.3 节与迭代一需求第 69 行，应**如实报告、不制造差值**。汇报时必须解释原因：本数据集每条评分的业务主键天然唯一，且不存在完全重复记录，因此该维度**没有可改进空间**。

> 编号 U1 与 U4 的区别需在报告中说明：若同一用户在不同时间对同一电影评分（业务上可解释为"重复观看后再次评价"），U1 会判违规但 U4 不会。本轮实测不存在该情况，但规则保留以应对清洗引入的重复。

### 4.4 Up-to-date（时效性）

**文档含义**：数据应足够新，能够反映所关注对象的当前状态。

**⚠️ 本维度最容易设计错误。** 若以"当前日期"为参照，则 2000–2003 年的数据全部不合格，而文档明确"数据年代较早并不必然属于错误"。因此本维度采用**两层设计**：

**第一层：时间可解释性（客观、可自动验证）**

| 编号 | 检查项 | 判据 |
| --- | --- | --- |
| D1 | `Timestamp` 可转为合理日期 | 能成功转换且落在 1970-01-01 之后 |
| D2 | `Timestamp` 落在数据集覆盖范围内 | 位于 2.2 实测 `[min, max]` 区间内 |
| D3 | 单位一致性 | 以**秒**为单位解释时落在 `[956703932, 1046454590]`；若按**毫秒**解释则超出该区间（用于检出单位混淆） |

```
Up-to-date_reliability = 100 × (1 − |R_violate_D1_D2_D3| ÷ |R_total|)
```

**第二层：时间新鲜度（参照 T2；T1/T2 已确定，本层已实现）**

```
freshness(r) = clamp( (t_r − T1) ÷ (T2 − T1), 0, 1 )
Up-to-date = 100 × (1 − 时间违规率) × mean( freshness(r) for r in R )
```

即 `Up-to-date = 第一层得分 × freshness 均值`。
时间不可解释的记录不会因其时间戳落在早期而获得高分。

**实测结果（`task_001`，已由独立复算验证逐位一致）**

| 项 | 值 |
| --- | --- |
| 时间违规率（第一层） | **0.0** —— 1,000,209 条全部可解释 |
| 第一层得分 | **100.0000** |
| freshness 合计 | 215,430.829879820289 |
| 参与计算记录数 | 1,000,209 |
| **freshness 均值** | **0.215385814245** |
| **Up-to-date 得分** | `100.0 × 0.215385814245` = **21.5386** |

**freshness 分布（T1/T2 为分位数切点的必然结果）**

| 区间 | 条件 | 条数 | 精确占比 | freshness |
| --- | --- | --- | --- | --- |
| 训练期 | `freshness = 0` | 700,144 | 69.9998% | 0（clamp 下界） |
| 验证期 | 线性区（含 4 条 `t == T1`） | 150,035 | 15.0004% | 0 ~ 1 线性 |
| 测试期 | `freshness = 1` | 150,030 | 14.9999% | 1（clamp 上界） |
| **合计** | — | **1,000,209** | 100% | — |

> 与 2.4 节的划分表是同一组数据。边界条件的说明见 2.4 节 ——
> 有 4 条记录的时间戳恰好等于 T1，按程序逻辑归入验证期。

> ⚠️ **该维度得分（21.5386）明显低于其他四维，这不是缺陷，必须解释清楚。**
>
> 因为 T1/T2 按分位数确定，**70% 的记录必然落在 T1 之前**，其 freshness 被
> clamp 为 0。均值 0.2154 的含义是"整体数据窗口的新近程度约 21.5%"，
> 是对时间分布的客观描述，**不是"质量差"的判据**。
>
> 依据 `docs/迭代一_Hadoop数据清洗与Agent基础.md` 第 51 行：
> "数据年代较早并不必然属于错误"。
>
> 因此本维度**不得单独作为数据质量的结论**，在汇报与前端展示中必须配合
> 上述说明使用。这也是本维度权重被设为 **0.10**（五维最低档）的原因。

**本方案明确声明：**

- 不将"评分发生在 2001 年"视为质量缺陷。
- 时效性得分的含义是"**在数据集自身的观测窗口内，数据的时间分布与新近程度**"，**不是**"数据相对今天的过时程度"。
- 若评价目标要求"数据必须反映当前状态"，则本数据集（2000–2003）在该意义上**完全不满足** —— 这一事实本方案不回避。
- 若 B/C 认为该维度难以支撑结论，可**降级为说明性指标**（只报告 D1–D3 与时间分布直方图，不给单一分数），并在报告中标注理由。

### 4.5 Consistent（一致性）

**文档含义**：数据元素的类型、格式和含义应一致、清晰，不同记录及数据表之间不应相互矛盾，例如日期格式和单位是否统一。

本维度分三类检查，这也是**本轮最可能产生真实改善的维度**。

**（1）跨表引用完整性（含"跨表数据不一致"）**

| 编号 | 检查项 | 判据 |
| --- | --- | --- |
| C1 | `ratings.UserID` 在 `users` 中存在 | 反连接（anti-join）为空 |
| C2 | `ratings.MovieID` 在 `movies` 中存在 | 反连接为空 |
| C3 | 两侧 `ID` 空间不冲突 | `ratings` 中 ID 的取值域与对应表定义域一致 |

```
C_ref = 100 × (1 − (|V_C1| + |V_C2|) ÷ (|ratings| × 2))
```

**（2）表内值域与格式一致性**

| 编号 | 检查项 | 判据 |
| --- | --- | --- |
| C4 | 同一 `MovieID` 只有一种 `Title` | 分组后 `distinct Title` 数 = 1 |
| C5 | 同一 `MovieID` 只有一种 `Genres` | 分组后 `distinct Genres` 数 = 1 |
| C6 | 同一 `UserID` 只有一组属性 | 分组后 `Gender/Age/Occupation/Zip` 各自 `distinct` 数 = 1 |
| C7 | `Genres` 内部无重复项、无空项 | 按 `\|` 切分后无重复、无空串（如 `Drama\|Drama`、`Drama\|`） |
| C8 | `Genres` 各项均属文档规定类别 | 属于固定类型集合（共 **18** 类，实测得到，见下方说明） |
| C9 | `Zip-code` 格式一致 | 全部为 5 位数字且**保留前导零**（未被读成数值）。**实测 81 条不合规**，明细见下 |
| C10 | `Title` 无首尾空白、无异常控制字符 | 未匹配 `^\s|\s$` 及非法字符。**实测 50 条含非 ASCII 特殊字符**，见下 |

**C8 的类别集合（实测 18 类，按字典序）：**

```text
Action, Adventure, Animation, Children's, Comedy, Crime, Documentary,
Drama, Fantasy, Film-Noir, Horror, Musical, Mystery, Romance, Sci-Fi,
Thriller, War, Western
```

> 实测 `movies.dat` 中出现的类别**全部落在这 18 类内，无未识别类别**（违规 = 0）。每部电影的类型个数分布为：1 类 2025 部、2 类 1322 部、3 类 421 部、4 类 100 部、5 类 14 部、6 类 1 部。

**C9 的不合规明细（实测共 81 条，占 6040 的 1.34%）：**

| 形态 | 条数 | 样例 | 判定 |
| --- | --- | --- | --- |
| 10 字符：ZIP+4 | **66** | `96707-1321`、`90035-4444`、`84112-2004` | 美国 ZIP+4 扩展格式，**属合法但非 5 位**，建议**修复**为 5 位主体（截取 `-` 前部分） |
| 6 位数字 | **11** | `495321`、`970025`、`444555` | 无法解释的多余数字，**建议隔离**而非擅自截断 |
| 7 位数字 | **3** | `5849574`、`2020010`、`0956456` | 同上 |
| 9 位数字 | **1** | `193122042` | 同上，疑似加拿大邮编或输入错误 |
| 前导零 | **662** | `0xxxx` 形式 | **不是问题**，只要按字符串读取即可保留；若被当作数值读入会丢失前导零，这正是 C9 要防的陷阱 |

> ⚠️ **处置区分很重要**：ZIP+4 那 66 条属于**格式差异**，可安全修复为 5 位；而 6/7/9 位的 15 条**无法确定正确值**，应按"隔离"处理，**不得**擅自截断后声称已修复（依据迭代一需求第 91 行）。

**C10 的实测说明：** 50 条标题含有 ISO-8859-1 范围内的特殊字符，例如 `Misérables, Les (1995)`、`Metisse (Café au Lait) (1993)`、`Eighth Day, The (Le Huitième jour ) (1996)`。**这些不是错误数据**，而是**编码处理是否正确**的判据：以 ISO-8859-1 正确读取则显示正常，误用 UTF-8 读取会出现乱码。本轮将其作为"编码一致性"的检查项。

```
C_format = 100 × (1 − Σ_check |V_check| ÷ Σ_check |R_check|)
```

**（3）维度合成**

```
Consistent = 0.5 × C_ref + 0.5 × C_format
```

权重 0.5/0.5 的理由：跨表引用错误只影响 `ratings`，格式错误散布三表；各占一半可避免任一类被另一方稀释。

> **本方案声明**：`movies.Genres` 与 `users.Occupation` 之间**不存在语义关联**，因此不做跨表值域交叉校验。`Zip-code` 与 `Occupation` 的地理一致性**无法验证**（数据集不含地区真值），见第 6 节。

## 5. 汇总与对比口径

### 5.1 综合分

```
Overall = 0.25 × Accurate
        + 0.25 × Complete
        + 0.15 × Unique
        + 0.10 × Up-to-date
        + 0.25 × Consistent
```

**权重设计依据：**

| 维度 | 权重 | 理由 |
| --- | --- | --- |
| Accurate | 0.25 | 值域合法性是后续一切分析的基础，权重最高档 |
| Complete | 0.25 | 关键字段缺失会直接使记录不可用，权重最高档 |
| Consistent | 0.25 | 跨表关联断裂会使整条记录失去分析价值，权重最高档 |
| Unique | 0.15 | 重复会污染统计结果，但本轮实测风险低，取次高档 |
| Up-to-date | 0.10 | 本数据集为历史快照且时间分布均匀，该维度区分度有限，取低档 |

> 是否设置综合分**由学生决定**（迭代一需求第 55 行）。本方案**设置综合分用于趋势概览**，但规定：**汇报与前端展示必须以五维明细为主，综合分不得替代明细**，因为加权会掩盖"某维度未改善"的事实。

### 5.2 同一口径的实现要求

Before 与 After 两次评分**必须调用同一份评分程序、同一套阈值、同一套权重**，仅输入数据集不同（依据：迭代一需求第 69 行）。

**实现约束：**

- 评分参数（阈值、权重、类别集合）集中在 `hadoop/config/` 的配置文件中，不硬编码。
- Before 与 After 使用**同一份配置文件**，程序记录配置内容的哈希值作为 `rule_version`。
- After 的评分对象是**清洗后的主数据集**，被隔离的数据**不计入** After 的分母，但必须在报告中被单独统计。

### 5.3 必须同时输出的绝对量

得分之外，以下绝对量必须输出（前端与 Agent 解释依赖它们）：

| 字段 | 含义 |
| --- | --- |
| `before_count` / `after_count` | 清洗前后记录数 |
| `fixed_count` | 修复的记录数 |
| `deduplicated_count` | 去重移除的记录数 |
| `isolated_count` | 隔离的记录数 |
| 各维度 Before/After 得分与差值 | 五维对照 |

## 6. 适用范围、无法验证的情况与局限

> 本节对应迭代一需求第 108 行"说明学生设计的评价方法、**适用范围和局限**；**未完成、无法评价和未验证的情况应清楚标注**"，必须随评分结果一并展示。

### 6.1 适用范围

本方案适用于 MovieLens 1M 三个 `.dat` 文件的**结构与格式质量评估**，以及清洗前后质量的**相对比较**。不适用于评价推荐算法的效果，也不用于评价数据的商业价值。

### 6.2 明确无法验证的情况

| 事项 | 为什么无法验证 |
| --- | --- |
| **用户属性真实性** | `users.dat` 的人口属性由用户自愿填写，GroupLens 未核验（引言第 67 行）。格式正确**不能**证明内容真实。 |
| **评分真实性（是否真实偏好）** | 数据集不含行为真值，"用户评了 5 分"是否反映真实喜好无法从数据判定。 |
| **`Zip-code` 与 `Occupation`/地区的一致性** | 缺少地区真值参照，无法交叉验证。 |
| **"用户名"层面的同一人判定** | 用户标识已匿名化，无法判断不同 ID 是否属于同一自然人。 |
| **同名电影是否为同一部** | 不同 `MovieID` 可能有相同标题（如翻拍），仅凭标题无法判定，需外部知识库。 |
| **时间戳的时区正确性** | 数据集未声明时区，本方案统一按 UTC 解释，可能存在固定偏移。 |
| **"评分行为分布异常"是否属于质量问题** | 文档第 33 行指出该现象需结合数据背景判断。本方案**不**将其计入准确性扣分，仅作为观察输出。 |

### 6.3 方法本身的局限

1. **合法性 ≠ 准确性。** 本方案的 Accurate 维度实际衡量的是"字段值合法率"，不能证明"值真实反映现实"。这是文档第 67 行提出的思考题"格式正确是否足以证明真实性"的答案：**不足以**。
2. **微平均对字段数敏感。** 4.1 的微平均使字段较多的表影响更大；已通过"每字段一次机会"缓解，但未做表级加权。
3. **Up-to-date 参照系是相对的。** 以 T1/T2 为参照衡量的是"数据集窗口内的新近程度"，**不是**绝对时效性。若应用场景要求"数据必须反映当前状态"，则本数据集（2000–2003）**在该意义上完全不满足**，本方案不回避这一事实。
4. **完整性分级含主观判断。** 4.2 中"必需字段"的划分基于业务可用性推理，属设计决策而非客观事实，不同划分会得到不同得分。
5. **权重为设计选择，非测量结果。** 5.1 的权重反映本团队对该场景重要性的判断，改变权重会改变综合分排序。
6. **得分提升不等于问题全部解决。** 经"隔离"处置的记录会提高 After 得分，但问题只是被移出主数据集，并未被修正（文档第 91 行）。
7. **0–100 不是概率或百分比质量。** 得分不表示"数据有 X% 是正确的"这一绝对意义。

#      判定为「二进制文件」并改变行为（-q / -c / -v 的结果会不一致，
#      -v 甚至会丢数据）。加 -a 强制按文本处理，或用 awk。
grep -acP '[^\x00-\x7F]' movies.dat
#   等价且更稳妥的写法：
awk '/[^\x00-\x7F]/' movies.dat | wc -l

# 4.1 A10 Title 缺结尾年份 / 年份越界（期望 0 / 0）
awk -F'::' '$2 !~ /\([0-9]{4}\)[[:space:]]*$/ {n++} END{print n+0}' movies.dat
awk -F'::' 'match($2, /\(([0-9]{4})\)[[:space:]]*$/, m) { if (m[1]<1900 || m[1]>2003) n++ } END{print n+0}' movies.dat

# 4.5 C6 同一 UserID 属性冲突条数（期望 0）
awk -F'::' '{k=$1; v=$2"|"$3"|"$4"|"$5; if(k in seen){ if(seen[k]!=v) bad++ } else seen[k]=v} END{print bad+0}' users.dat
