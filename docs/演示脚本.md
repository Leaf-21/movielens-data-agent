## 零、演示前自检（提前 10 分钟做）

### 0.1 启动三件套

**推荐：一键脚本**（成员C提供，自动导出 JAVA_HOME/HADOOP_HOME，按序拉起 Hadoop → Agent → 前端并做健康检查）：

```bash
bash scripts_setup/install_data.sh     # 首次 / 仓库被重新克隆后必做：解压数据并校验和
bash scripts_setup/start_all_wsl.sh    # 启动三件套；停止：bash scripts_setup/stop_all_wsl.sh
```

**备选：手动三终端**（顺序不能反，Agent 依赖 Hadoop；WSL 里 `python` 不存在，一律用 `python3`）：

```bash
# 前置：数据落位 + Hadoop 环境变量（一键脚本会做这两件事，手动路线需自己来）
bash scripts_setup/install_data.sh
export JAVA_HOME="$HOME/opt/jdk-17.0.20.1+1"    # 指向本机实际 JDK（ls ~/opt/jdk-* 确认）
export HADOOP_HOME="$HOME/opt/hadoop"
export HADOOP_CONF_DIR="$HADOOP_HOME/etc/hadoop"
export PATH="$HADOOP_HOME/bin:$PATH"
export ML_STREAMING_JAR="$HADOOP_HOME/share/hadoop/tools/lib/hadoop-streaming-3.4.1.jar"

# 终端1：成员A 的 Hadoop 服务（默认 8080，数据目录默认为仓库内 data/ml-1m-v2）
python3 hadoop/src/server.py

# 终端2：成员B 的 Agent 服务（默认 8090）
python3 agent/src/api.py --port 8090

# 终端3：成员C 的前端服务（默认 8000，反代 /api 到 8090）
python3 frontend/src/serve.py --port 8000
```

打开 <http://127.0.0.1:8000>，右上角应显示 **Agent 在线**（绿色）。
若显示"Agent 离线"，检查终端2是否起来了、端口是否一致。

## 一、演示流程（约 5–8 分钟）

### 第 1 步：介绍系统（30 秒）

> "这是 MovieLens 数据治理 Agent 系统。用户只需用自然语言提一次需求，
> Agent 就会自动调用 Hadoop 完成：清洗前评分 → 数据清洗 → 清洗后评分 → 结果对比，
> 并把五维质量得分、数据处理情况、评估报告展示出来。
> 整个过程用户不需要手动跑命令、上传文件或点中间步骤。"

### 第 2 步：输入需求并提交（30 秒）

1. 指着输入框里的默认提示念一遍：

   > "请使用默认规则清洗 MovieLens 1M，评估清洗前后的 Accurate、Complete、
   > Unique、Up-to-date、Consistent 五个维度，并说明处理了哪些问题、
   > 还有哪些问题无法解决。"

2. 指出下方示例可一键填充（**只评估不清洗**、**关注未解决问题**）。
3. 点击 **开始执行**。

> 说明：数据版本 `movielens-1m-v2`、规则版本 `default` 是可选参数，
> 不填也会走系统登记的默认方案。

### 第 3 步：展示执行状态（30 秒）

任务提交后会依次看到：

- 顶部状态徽章：`排队中` → `运行中` → `已完成`；
- 阶段进度条：**解析需求 → 清洗前评分 → 数据清洗 → 清洗后评分 → 生成报告 → 完成**，
  已完成的阶段变绿、当前阶段变蓝；
- 任务 ID、当前阶段等元信息。

> 强调："用户可以随时知道任务跑到哪一步、是否失败。失败时会明确告知是哪个环节、
> 什么原因，而不是笼统地报错。"

### 第 4 步：五维评分对比（核心，1.5 分钟）

指向 **"五维质量评分对比"** 表格：

- 五列分别是：维度、清洗前、清洗后、**变化**、进度条；
- 逐行念关键变化，例如：
  - 准确性 `97.74 → 99.95`（+2.21）
  - 完整性 `97.99 → 100.00`（+2.01）
  - 时效性 `29.59 → 21.22`（**-8.37**）
  - 一致性 `96.80 → 99.92`（+3.13）
- 若接口返回综合分，底部会多一行 **综合分（加权）**。

> **重点解释时效性为什么下降**（这是老师大概率会问的点）：
> "时效性不是简单地'越高越好'。它的算法衡量的是数据的新近程度，清洗前
> 一些异常时间戳（毫秒时间戳、2100 年这种）被截断到上界，反而让得分虚高；
> 清洗后回落到真实水平。这属于数据本身的客观反映，不是清洗引入的新问题。
> 报告里也明确标注了这一点。"

### 第 5 步：数据与规则版本、时间边界（30 秒）

指向 **"数据与规则版本 · 时间边界"**：

- 数据版本：`movielens-1m-v2-clean-v1`
- 规则版本：`rule-v2`
- **T1**（训练期截止）/ **T2**（验证期截止）

> "T1/T2 是后续迭代统一使用的时间边界，本轮确定下来，保证大家不混用不同
> 时间范围的数据产物。"

### 第 6 步：数据清洗结果（1 分钟）

指向 **"数据清洗结果"**：

- 数据量：`原始 1,161,652 → 清洗后 1,006,021`
- 修复 `65`、去重 `55,739`、隔离 `99,892`
- 分表统计（ratings / movies / users 各自的输入、清洗后、修复、去重、隔离）

> **重点强调数据处置的区别**（需求反复强调的易错点）：
> "'修复'是把值改对了；'去重'是删掉了重复记录；'隔离'是把无法修复的记录
> 移出主数据集单独保存。**隔离不等于修复** —— 问题本身没有被解决，
> 只是把坏数据挪走了。这一点页面上三类是分开统计的。"

### 第 7 步：问题与未解决问题（1 分钟）

- **"识别到的问题及处置"**：每条问题带处置标签（修复/去重/隔离/保留）+ 严重度 + 条数 + 原因。
- **"未解决问题"**（黄色高亮，带计数）：例如
  - 跨表关联断裂（ratings 引用的 UserID 在 users 中不存在）；
  - 同一主键的多条合法但冲突的记录（清洗只做了确定性选择，**未真正解决**）。

> "我们不会把'删掉/隔离了记录'说成'问题解决了'。清洗完成不代表所有质量问题
> 都消失了，这里如实列出还剩哪些、为什么解决不了。"

### 第 8 步：评估报告（30 秒）

指向 **"评估报告"**，含四部分：

1. **改善项**：各维度前后变化与原因；
2. **未解决问题**；
3. **评价局限**：哪些情况无法验证（如用户属性真实性、时区、同名电影等）。

### 第 9 步：清洗后数据样例（20 秒）

指向 **"清洗后数据样例"**。若接口未返回样例，页面会明确标注"不可得"，
**不会编造**。

### 第 10 步：追问 Agent（核心交互，1 分钟）

在 **"继续追问 Agent"** 输入框依次提问（可直接点下方的示例链接）：

1. `为什么 Complete 提高了？`
2. `删除了多少条数据？`
3. `哪些数据被隔离了？`
4. `为什么有些问题没有解决？`

> "追问的回答都基于本次任务的真实数据，不是编的。被隔离的记录如果问'算不算
> 修复'，它会明确回答'不算'。"

## 二、演示备用话术（应对提问）

| 可能被问到 | 怎么答 |
| --- | --- |
| 分数是不是写死的？ | 页面所有数值都来自 Agent 接口的实际返回，前端代码里没有任何硬编码分数；测试里做了"三层一致性"校验（Hadoop→Agent→前端逐字段一致）。 |
| 时效性为什么降了？ | 见第 4 步，是异常时间戳被清洗后回落的客观反映，不是新问题。 |
| 隔离的记录算修复了吗？ | 不算。隔离是把无法修复的记录移出主数据集，问题未解决，页面单独列了"未解决问题"。 |
| "只评估不清洗"能行吗？ | 可以。示例里就有。此时清洗后的数值会留空显示"—"，而不是显示 0（未执行 ≠ 得分为 0）。 |
| 任务失败会怎样？ | 状态徽章变红，明确显示失败环节和原因；已完成环节的结果会作为"部分结果"如实展示，缺失部分留空。 |
| 前端和后端怎么连的？ | 前端调 Agent 的三条接口（创建任务/查状态/取结果）+ 追问接口；前端服务用反向代理把 `/api` 转发到 Agent，避免跨域，前端不直接碰 Hadoop。 |
